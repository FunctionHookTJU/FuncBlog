2–3 用户界面设计与详细设计工具

2.1 两种"交互"要先分清

课件第 36 页给了一张很干净的对照图：

        用户 ──→ 软件 ←── 其它软件
              ↑        ↑
          人机交互   软件接口
  • 软件接口：软件与其他软件系统交互，靠接口（API、协议、文件格式）。
  • 人机交互：软件与用户交互，靠界面（输入、输出）。

补这两件事经常被混为一谈：学生做项目时说"我要设计接口"，往往指的是 REST API；而用户界面设计是另一套东西。区分它们很重要，因为评价标准完全不同：接口看的是"正确性、稳定性、兼容性"，界面看的是"能不能用、好不好用、爱不爱用"。

2.1 四种人机交互方式

课件第 37 页给了四种，每一种都带"代价"：

方式 例子 特点
文本 DOS、Linux 命令行 须记忆命令、不友好
图形化界面 窗口、按钮、对话框 直观、简洁、友好
语音 Siri、手机导航、机器人交互 解放双手，需要麦克风
手势 无人机交互 准确性不高，需要视频传感器

补这张表的重点是"代价"那一列：语音和手势看起来很"未来"，但课件明确写了它们对硬件的依赖和准确率问题。选择交互方式的第一原则不是"先进"，而是"匹配场景"：坐在电脑前做表格，键盘鼠标永远比语音快；在厨房手上全是面粉，语音才有价值；在嘈杂车间，语音又不行了。

课件还针对语音给了四条设计考虑（PPT 第 40 页）：计算机能否准确理解语音；用户能否听得到、听得清；能否在不同环境（嘈杂/安静）下调整音量；能否针对用户位置定向播放。

2.2 人机交互的三个关键

课件第 41 页，这三条是界面设计的"验收标准"：

关键 含义
用户的满意度 用户通常把界面视为软件本身；界面设计的质量直接决定用户对系统的评价
方便输入 快速、便捷、准确、友好的输入（鼠标、点击、选择）
直观输出 直观、显式、可理解、简洁的输出（所见即所得、图形展示）

补"用户把界面视为软件本身"这句话是全节的钥匙。一个后台算法再优雅、架构再合理，只要界面难用，用户就认为"这个软件不行"。界面对用户来说是软件的"全部"——这也解释了为什么第 7 讲要用整整一节讲界面，而不是把它归到"实现细节"里。

以用户为中心的设计（UCD）

课件第 42 页给了三步：

  1. 将用户特征作为界面设计决策的依据：识别用户及其特征（操作习惯、文化背景、教育程度）；分析用户与系统之间的交互信息及合适的手段。
  2. 尽可能获得用户反馈并据此改进：怎么获得？软件原型；从用户立场出发，便于理解和操作。
  3. 以用户体验感受和满意度为依据评审交互设计。

补注意第 2 条又把"原型"搬出来了——这已经是原型第三次出现（第 3 讲过程模型、第 4 讲需求获取、这里）。这不是重复，是同一个工具在不同阶段的不同用途：第 3 讲用它应对需求不确定，第 4 讲用它导出需求，这里用它验证界面。一个好工具会在整个生命周期里反复出现。

四类界面元素

课件第 43 页的分类是全课程最实用的界面设计知识，考试常考"这个控件属于哪类"：

类别 定义 例子
静态元素 与系统运行状态无关，没有变化 文本、图标、图形、图像
动态元素 与运行状态和业务逻辑相关，不允许用户修改 不可编辑文本、表格、图标、图形
用户输入元素 由用户填写或选择 编辑文本框、单选按钮、多选框
用户命令元素 点击后激活后端业务处理或刷新界面 按钮、菜单、超链接

补区分静态与动态的分界线是"会不会随数据变化"：界面上的"欢迎使用"是静态的（永远一样），"当前电量 87%"是动态的（跟着状态变）。区分动态与输入的分界线是"用户能不能改"：电量显示不能改，密码框能改。

课件第 47 页给了一个真实例子——"MonitoringUI"的设计类图：

MonitoringUI
  -connectingRobotStatus    ← 动态元素：显示与机器人的连接状态
  -batteryofRobot           ← 动态元素：显示机器人剩余电量
  <<input>> -openCamera     ← 用户输入元素：打开/关闭摄像头
  -videoRegion              ← 动态元素：显示老人视频并播放语音
  +monitorElder             ← 用户命令：监视老人状况
  +controlRobot             ← 用户命令：控制机器人运动
  +interactElder            ← 用户命令：视频/语音交互
  +configureSystem          ← 用户命令：配置系统

补这张图示范了"界面也要建模"：界面的每个元素都变成类的一个成员，元素类型用构造型（<<input>>）标注。好处是界面和业务逻辑同样可评审、可追踪——不会出现"设计文档里没有这个按钮，代码里却有"的情况。

用顺序图表示界面跳转（PPT 第 45 页）：QueryTrainUI → QueryResultUI，箭头上标 [点击 查询车票 按钮]。这是把"用户操作 → 界面切换"形式化的标准做法。

十个微交互案例的共同点

课件第 48–58 页用了十页讲"细节之处见真章"，列举支付宝/微信付款自动亮屏、iOS 复制时放大镜、B 站注册时动漫人物遮眼、iOS 后台缩略图高斯模糊、Google Map 步行距离过长小人拄拐、iPhone 时钟图标实时显示时间、网易云断网默认跳"我的音乐"、高德加载可取消、滴滴预测目的地、腾讯视频"只看某人"。

课件给了一个三层框架：能用（能解决问题）→ 好用（省心省力，不焦虑）→ 爱用（极少产品做到）。

补这十个案例的共同点不是"有趣"，而是三条设计原则：

  1. 消除一次多余的操作（自动亮屏、预测目的地）——减少步骤；
  2. 消除一次可能的困惑（放大镜、断网跳本地、可取消加载）——及时反馈、无须记忆；
  3. 保护一次可能的暴露（遮眼、高斯模糊）——隐私与情境感知。

换句话说，它们全部对应第 6 讲界面七准则里的某一条。 好的界面设计不是灵感，是准则的逐条落实。

3 详细设计：四种描述工具

课件第 61–63 页先把位置说清楚：

详细设计是高层设计和底层实现之间的桥梁。

关注点的变化（PPT 第 61 页）：

体系结构设计（结构性/全局性/关键性/粗粒度）
   → 人机界面设计
   → 详细设计（过程性/局部性/细节性/细粒度）
   → 整合与验证
（全程：迭代设计、反复精化、持续优化）

详细设计的任务：开发一个可以直接转换为程序的软件表示，即对系统中每个模块的内部过程进行设计和描述。

四种常用工具：

① 流程图

最传统，用方框、菱形、箭头表示顺序、选择、循环。优点是直观；缺点是无法强制结构化（容易画出"面条代码"）。

② N-S 图（结构化流程图 / 盒图）

只用顺序、选择、循环三种基本结构组合而成，完全取消了箭头，因此天然保证单入口单出口。

基本构件（PPT 第 64–65 页）：顺序结构（块 1 块 2 块 3 自上而下）、选择结构（条件 T/F 分两块）、多分支选择（Case I=1,2,3）、当型循环（当条件成立时反复执行）、直到型循环（直到条件成立）。

补N-S 图的核心价值是"画不出坏结构"：因为没有箭头，你无法表达 goto，也就无法写出任意跳转的流程。这是"用表示法约束思维"的典型例子——比靠纪律要求程序员"不要用 goto"有效得多。

③ PAD 图（问题分析图，Problem Analysis Diagram）

用二维树形结构表示程序控制流，从左向右展开，基本结构与 N-S 类似但更紧凑（PPT 第 66 页）：顺序（任务 1、2、3 自上而下）、选择（条件 T/F 分左右）、多分支选择（控制变量 + 值 1..n）、WHILE 型循环（先判定）、UNTIL 型循环（后判定）。

课件第 67 页给了"数组排序"的 PAD 图完整示例，演示了自顶向下、逐步求精的三步：先画"排好第 h 个 X[h]"的总框 → 细化成"找最大值 + 交换" → 再细化"找最大值"的循环 → 连接成完整 PAD 图。

补PAD 图的独特之处是"可以机械地转成代码"：它的每个结构都对应一段固定形式的代码（顺序→连续语句，选择→if/else，WHILE→while，UNTIL→do-while）。所以它是四种工具里离代码最近的一种。

④ PDL（程序设计语言 / 伪码）

用自然语言和程序语言混合书写，介于设计与代码之间。优点是可读性好、便于评审；缺点是没有图形约束，容易写得太随意。

补四种工具怎么选：需要和用户/非技术人员沟通 → 流程图；需要保证结构化 → N-S 图；需要精确到可直接编码 → PAD 图；需要快速记录思路 → PDL。实际工程中 PDL 用得最多，N-S 和 PAD 主要用于教学与评审。
