1–2 程序设计语言与结构化程序设计

第 8 讲的三节标题起得很有意思：语言选择是"兵器"，面向对象程序设计是"剑谱"，程序设计风格是"心决"。兵器可以换，剑谱要练熟，心决决定你能走多远。

编码到底在做什么

课件第 2 页给了定义：

编码的目的：使用选定的程序设计语言，把模块的过程性描述（不可执行的）翻译为用该语言书写的源程序（可执行的）。

课件第 4–5 页强调编码的双重身份：

身份 含义
软件创作 自由开展代码创作，发挥创新性和主观能动性，创作出算法精巧、运行高效的代码
软件生产 按质量保证的规范和要求生产高质量代码，约束编程行为，防止随意性，确保满足工程化开发要求

输入是三个设计模型（体系结构、用户界面、详细设计），输出是"高质量的程序代码"。

补这个"双身份"直接解释了第 8 讲为什么既讲"结构化程序设计"（创作方法论）又讲"程序设计风格"（生产规范）：前者关心"怎么想清楚"，后者关心"怎么让别人看懂"。两者缺一不可——只会创作的人写出天书，只会守规范的人写出平庸代码（第 2 讲"创作 + 生产"的公式在这里再次生效）。

1 程序设计语言的分类

按级别分两类（PPT 第 6 页）：

类别 内容 特点
低级语言 机器语言、汇编语言（二进制指令集，或操作码符号化） 依赖特定机器；使用复杂、繁琐、费时、易出差错
高级语言 表示方法更接近待解问题 一定程度上与具体机器无关；易学、易用、易维护；极大提高软件生产效率

高级语言的三代（PPT 第 7 页）：

类型 代表 主要用途
传统高级语言 BASIC、FORTRAN、ALGOL 科学计算（航空航天、地质勘探、天气预报、建筑工程）
通用结构化语言 PASCAL、PL/1、C、Ada 嵌入式实时系统、多任务、中断处理、任务间同步通信、复杂 I/O、表处理
面向对象语言 C++、Java、C#、Python 信息管理系统、桌面程序、互联网程序、大数据

补课件第 8 页专门提了 C# 的 TIOBE 表现（长期稳居前 10、蚕食 Java 份额、在 Web 后端和游戏领域流行，得益于 Unity）。这类"语言排行榜"的内容考试不会考，但它传达了一个判断：语言是有生命周期的，选语言时要看生态而不是看语法优雅。

选择语言的五条准则

课件第 9 页，这五条可以直接当简答题答案：

# 准则 要点
1 项目的应用领域 尽量选适合该领域的语言（科学计算 vs 管理系统 vs 嵌入式）
2 软件的执行环境 要选机器上能运行、且有相应支持软件的语言
3 性能因素 结合工程具体性能要求考虑
4 数据结构的复杂性 根据语言构造数据结构类型的能力选取
5 开发人员的知识水平与心理因素 尽量避免受外界影响，盲目追求高、新的语言

补第 5 条是全表最"人味"的一条。技术选型最常见的失败不是"选错了语言"，而是"选了团队不会的语言"。用一门团队精通的老语言写出能维护的系统，胜过用最新语言写出没人看得懂的系统。 这和 C++ 之父那句"限制你的不是你知道什么，而是你以为你知道什么"是一体两面。

2 结构化程序设计

来历（PPT 第 17 页）：概念最早由 E. W. Dijkstra 提出，是结构化开发方法的重要组成部分。

定义：一种设计程序的技术，采用自顶向下、逐步细化的设计方法和单入口、单出口的控制结构。

基本原则：功能的分解与抽象，体现"先全局后局部、先抽象后具体"，使程序层次结构清晰、易读、易理解、易验证。

三种控制结构：顺序、选择、循环——"既保证程序结构清晰，又提高程序代码的可重用性"。

四条原则（PPT 第 18 页）：

  1. 用语言中的顺序、选择、重复等有限的基本控制结构表示程序；
  2. 选用的控制结构只准许有一个入口和一个出口；
  3. 程序语句组成容易识别的块（Block），每块只有一个入口和一个出口；
  4. 复杂结构应该用基本控制结构进行组合嵌套来实现。

补为什么要"单入口单出口"？ 因为程序的复杂度主要来自控制流的交叉。一个模块如果可以从多个地方进入、从多个地方退出，那么"这段代码在什么状态下执行"就无法靠阅读局部代码判断——你必须知道所有调用它的上下文。单入单出保证了"读一段代码就能理解一段行为"，这是可读性和可测试性的基础（第 9 讲的单元测试也是按"模块"为单位做的，多入口的模块根本没法单独测）。

案例 1：break 与 continue 的流程图

课件第 19 页给了一段带 break / continue 的 C 代码：

for (a = 1, b = 1; a <= 100; a++) {
    if (b >= 20) break;
    if (b % 3 == 1) { b += 3; continue; }
    b -= 5;
}

它画的流程图特意标出了"单入口 M1 / 单出口"。

补这个例子想说明：即使代码里用了 break 和 continue 这种"中途跳转"，只要跳转的目标边界是模块本身（跳出循环但不跳出模块），整个模块仍然是单入口单出口的——结构化不等于禁止 break，而是禁止"跳出模块"。真正破坏结构化的是 goto 到模块外、或者多个 return 散落在深层嵌套里。

案例 2：二分法求根的结构化改造

课件第 20–22 页给了一个非常精彩的"坏结构 → 好结构"改写。

问题：对区间 [a, b] 上连续且 f(a)·f(b) < 0 的函数，不断把零点所在区间一分为二，逐步逼近零点。

初始结构（用了 for + break）：

F0 = F(a); F1 = F(b);
if (F0 * F1 <= 0) {
    X0 = a; X1 = b;
    for (i = 1; i <= n; i++) {
        Xm = (X0 + X1) / 2;  Fm = F(Xm);
        if (abs(Fm) < eps || abs(X1 - X0) < eps) break;
        if (F0 * Fm > 0) { X0 = Xm; F0 = Fm; }
        else X1 = Xm;
    }
    printf("%d\n", Xm);
}

改进后（用 while + 结束标志）：

F0 = F(a); F1 = F(b);
if (F0 * F1 <= 0) {
    X0 = a; X1 = b; i = 1; finish = 0;
    while (i <= n && finish == 0) {
        Xm = (X0 + X1) / 2;  Fm = F(Xm);
        if (abs(Fm) < eps || abs(X1 - X0) < eps) finish = 1;
        if (finish == 0)
            if (F0 * Fm > 0) { X0 = Xm; F0 = Fm; }
            else X1 = Xm;
        i++;
    }
    printf("%d\n", Xm);
}

补这个改写体现了三个结构化原则：①把"两种退出条件"（循环次数到 / 精度够）合并成一个循环条件，避免 break 造成的多出口；②用 finish 标志把"退出原因"变成显式状态，读代码时一眼能看出逻辑；③循环体内部只保留一个判断入口。代价是代码变长了——这正是结构化的常态：用一点冗长换可读性。

结构化程序设计的步骤

课件第 23 页：

  1. 程序设计是一个由粗到细的"渐进"过程（逐步细化）；
  2. 程序设计不仅包括控制结构的设计，也包括数据结构的设计，二者都要一步步细化。

具体步骤：提出和分析问题 → 确定数学模型 → 设计算法 → 模块化编程、整体编译运行 → 设计优化（结构、算法、功能、效率）。

结构化 vs 面向对象

课件第 24–26 页用"咖啡店程序"做了对比，结论很克制：

结构化 面向对象
组织方式 按顺序从上到下执行，函数 + 嵌套 if 类 + 属性 + 方法，实例化后调用
优点 构建小程序最简单，直观 减少重复逻辑、减少嵌套、易扩展
缺点 重复逻辑多、嵌套 if 多、阅读和修改困难 简单项目里用 OOP 会让人不知所措
适用 简单的项目 大型代码库

课件的总结值得原样引用：

• 两种范式都不是完美的（在简单的项目中使用 OOP 可能会让人不知所措）。 • 这只是解决问题的两种方法；还有其他方法。 • OOP 用于大型代码库，而结构化编程主要用于简单的项目。

补这段总结比"OO 优于结构化"的老套说法高级得多。它承认了"没有最好的范式，只有匹配规模的范式"——这和过程模型的选择（第 3 讲）、架构风格的选择（第 7 讲）是同一种思维方式：工程判断永远是"在特定约束下选最合适的"，而不是"选最先进的"。

时间效率优化的四条

课件第 27 页给了四条，顺序很重要：

  1. 不考虑时间因素的前提下开发并精简软件结构（先做对、做干净）；
  2. 寻求设计结构中的"关键路径"和"关键事件"，仔细设计该模块的实现算法（只优化瓶颈）；
  3. 选择合适的高级编程语言，提高程序的编译效率；
  4. 在效率和实现功能之间寻求平衡点——不为一些不必要的功能耗费大量时间，以致得不偿失。

补第 1 条是 Knuth 那句名言的翻版："过早优化是万恶之源"。第 2 条是它的操作化：先测量，再优化——因为 90% 的时间花在 10% 的代码上，优化错了地方等于白干还引入 bug。

四道选择题（课件第 28 页原题）

1. 结构化程序设计的一种基本方法是（ ） A. 筛选法　B. 递归法　C. 迭代法　D. 逐步求精法 → D。结构化程序设计的核心方法是"自顶向下、逐步细化"。

2. 结构化程序设计主要强调的是（ ） A. 程序的效率　B. 程序执行速度　C. 程序易读性　D. 程序的规模 → C。结构化是为了"易读、易理解、易验证"，不是为了效率（甚至常常牺牲效率换可读性）。

3. 程序的三种基本控制结构的共同特点是（ ） A. 不能嵌套使用　B. 只能用来写简单程序　C. 已经用硬件实现　D. 只有一个入口和一个出口 → D。三结构的共同点就是单入单出；而且它们可以任意嵌套组合（所以 A、B 错）。

4. 多选题：结构化程序设计优化包括（ ） A. 结构的优化　B. 算法的优化　C. 提高程序的编译效率　D. 在效率和实现功能之间寻求平衡点 → ABCD。四条全对，正好对应上一节"时间效率优化的四条"。
