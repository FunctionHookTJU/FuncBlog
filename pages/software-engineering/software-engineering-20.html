2.5–3 动态模型、功能模型与需求变更

对象模型建好之后，还有两件事：让对象"动起来"（动态模型），和让数据"流起来"（功能模型）。

2.5 动态模型

定义（PPT 第 85 页）：动态模型表示瞬时的、行为化的系统的"控制"性质，规定对象模型中对象的合法变化序列。

构建方式：每个类的动态行为用一张状态图描绘，各个类的状态图通过共享事件合并起来（交互图），构成系统的动态模型。所以：

动态模型是基于事件共享而互相关联的一组状态图的集合。

行为的三级分类（PPT 第 86 页）：

级别 例子
系统行为 创建、删除、复制、转存
对象自身的简单行为 读、写属性值
对象自身的复杂行为 计算或监控

发现服务的五个环节（PPT 第 87 页）：识别服务 → 对象的审查与调整 → 认识对象的主动行为 → 服务的命名与定位 → 描述服务。

从脚本到状态图：五步链条

（1）编写脚本（PPT 第 88 页）

脚本是系统在某一执行期间内出现的一系列事件，描述用户与目标系统之间一个或多个典型的交互过程。目的：保证不遗漏重要的交互步骤，确保交互过程的正确性和清晰性。编写顺序：先写正常情况，再考虑特殊情况。

课件给了 ATM 的两份脚本（第 89–90 页），摘录正常脚本的前几步：

• ATM 请储户插卡；储户插入一张现金兑换卡
• ATM 接受该卡并读它上面的分行代码和卡号
• ATM 要求储户输入密码；储户输入密码
• ATM 请求总行验证卡号和密码，总行要求"39"分行核对，然后通知 ATM 该卡有效
• ATM 要求储户选择事务类型；储户选择"取款"
• ATM 要求输入取款额；储户输入"1000"
• ATM 确认取款额在限额内，要求总行处理；总行转给分行，分行处理完并返回余额
• ATM 吐出现金并请储户拿走；储户拿走
• ATM 询问是否继续；储户回答"不"
• ATM 打印账单，退卡

异常脚本则是：密码输错 → 拒绝 → 重新输入 → 中途按"取消" → 退卡。

补两份脚本的差别就是"主成功场景"和"替代场景"（第 4 讲已讲）。写脚本的价值在于它是"人类语言"，用户能看懂并能指出错漏——这正是第 5 讲开头说的"初步需求不具体"的解药。

（2）设想用户界面（PPT 第 91 页）：在写脚本时顺手把界面画出来，能进一步暴露需求的模糊处。

（3）画事件跟踪图（PPT 第 92–94 页）

脚本用自然语言写，"往往不够简明，阅读时产生二义性"。事件跟踪图把它形式化：

      对象1   对象2   对象3   对象4
        │       │       │       │
 事件1  ●───────┼───────┼───────┤
        │       │       │       │
 事件2  ├───────●───────┼───────┤
        │       │       │       │

横向是对象（每列一个对象），纵向是事件发生顺序。分析每个脚本，提取所有外部事件（用户交互的信号、输入、输出、中断、动作），并区分每类事件的发送对象与接收对象。

补事件跟踪图就是"顺序图的前身"——它只有"谁给谁发消息"的二维网格，没有生命线和激活期。所以会画事件跟踪图，顺序图就自然会画，只是加上对象框、生命线和箭头样式而已。

（4）画状态图（PPT 第 95–97 页）

三个基本概念：

概念 定义
事件 引起对象状态转换的控制信息，是现实世界事件的抽象
状态 对象在其生命周期中某个特定阶段所处的某种情形
行为 对象达到某种状态时所做的一系列处理操作

画法：状态用圆角框/椭圆，框内标状态名，行为用 do: 标明；箭头标 事件[条件]。

课件给了 ATM 类、分行类、总行类三张状态图。ATM 的状态包括：主屏、要求密码、验证账号、处理事务、要求金额、要求类型、吐出现金、打印账单、退卡、取消、等待网络响应、不可读的卡……每张状态图内部都是 Do: 某动作。

补注意"每个类一张状态图"这个做法：动态模型不是"整个系统一张大状态图"，而是"每个有显著状态变化的类各一张"，然后通过共享事件把它们拼起来（ATM 发出"请求验证账户"，总行收到并转移状态——同一个事件把两张图缝在一起）。这正是"基于事件共享而互相关联的一组状态图"这句话的含义。

（5）从事件导出服务（PPT 第 98 页）

这一页很关键，它把动态模型和对象模型接上了：

状态图中发往对象的事件，也就是该对象接收到的消息，因此该对象必须有由消息选择符指定的操作，这个操作修改对象状态并启动相应的服务。

ATM 的例子：发往 ATM 的"中止"事件 → 启动"打印账单"服务；发往分行的"请分行验卡" → 启动"验证卡号"服务；"处理分行事务" → 启动"更新账户"服务。

补这条链是 OOA 的精髓：脚本 → 事件 → 状态迁移 → 服务（方法）。也就是说，方法不是"想出来的"，是"事件逼出来的"。这比"先想这个类应该有什么方法"可靠得多——因为你无法凭空想出所有方法，但你可以列出所有事件。

2.6 功能模型

定义（PPT 第 99 页）：功能模型表示变化的系统的"功能"性质，指明系统应该"做什么"，因此更直接地反映用户对目标系统的需求。它由一组数据流图组成。

课件有一句很诚实的判断：

与对象模型和动态模型比较起来，数据流图并没有增加新的信息，但建立功能模型有助于开发人员更深入地理解问题域，改进和完善自己的设计。

补"没有增加新信息"这句话是理解功能模型地位的关键：它不产生新知识，它的作用是交叉验证——如果数据流图里出现了一个"没有来源的数据"，或者一个"没人使用的输出"，就说明前面两个模型漏了东西。它是校验工具，不是主模型。

两级数据流图：

（1）基本系统模型（PPT 第 100–101 页）：由若干数据源点/终点和一个处理框组成，这个处理框代表系统加工、变换数据的整体功能。它指明了目标系统的边界。

ATM 的基本系统模型：

       现金兑换卡
储户 ──────────────→ ┌─────────┐ ──→ 现金、账单、信息 ──→ 储户
     ←────────────── │ ATM系统 │
       分行代码、卡号  └─────────┘
       密码、事务类型、金额

（2）功能级数据流图（PPT 第 102 页）：把单一处理框分解成若干处理框，描述系统加工、变换数据的基本功能。ATM 的例子分解为：接收输入 → 验卡 → 验证密码 → 检查账户 → 更新账户 → 产生输出 → 显示出错信息 → 选定分行。

（3）细化定义服务（PPT 第 103 页）

两个要点：

  • 数据流图的每个处理框，都与一个（或若干）对象上的操作相对应。要仔细对照状态图和数据流图，才能正确确定对象应提供的服务。ATM 例：状态图说分行应提供"验证卡号"，数据流图上对应的处理框叫"验卡"，按实际功能看，服务名应为"验卡"。
  • 利用继承减少冗余操作：尽量抽出相似类的公共属性和操作，建立新父类。

三模型的分工（课件第 104 页原话）

三个模型从三个不同的角度对所要开发的系统进行了描述，相互补充、相互配合，使开发人员能够更全面地认识系统。

  • 对象模型：以对象、属性、关系和操作的形式描述系统结构；
  • 动态模型：描述系统的内部行为；
  • 功能模型：从用户观点描述系统功能。

功能模型指出发生了什么，动态模型确定什么时候发生，而对象模型确定发生的客体。

补这三句话可以用来判断"某个问题该用哪个模型回答"：

  • 问"系统有哪些数据实体"→ 对象模型；
  • 问"用户下单后系统按什么顺序处理"→ 动态模型；
  • 问"输入到输出经过哪些变换"→ 功能模型。

3 需求变更案例：从门店到集团

课件第 106–117 页用"一个小门店成长为多元化集团"讲了需求如何演化。它的结构非常清晰，值得完整看一遍：

阶段 组织与业务变化 软件应对
① 小门店 一个人经营，十几平米，采购+摆货+销售 Excel 三张表（采购记录、商品信息、销售），用 ER 模型描述逻辑结构（采购记录:商品信息 = 多:一）
② 小超市 雇了几个店员，货品更丰富，日交易量成倍增长 Excel 撑不住了 → 买轻量级 ERP，只买核心模块以控成本
③ 加 CRM 设计会员积分制度，开微信公众号让客户查积分 ERP 里的 CRM 模块功能有限（不支持对接微信、营销弱）→ 另买CRM 软件 + 外包定制开发
④ 中型连锁 五家店、几百员工，管理分工成型 引入 OA、HRM，重构 ERP；建数据仓库（DW）+ BI，并做数据集市（Data Mart）
⑤ 大客户业务 开展 2B，成立大客户销售部 实施操作型 OCRM，独立于现有 CRM 重新开发，边界清晰、便于各自演化

补这个案例的价值在于它演示了三种典型的"软件演化方式"：

  1. 换工具（Excel → ERP）：原来的方案在规模和协作上撑不住了；
  2. 加系统（ERP + CRM + OA + HRM）：单一系统无法覆盖所有业务，走向"系统之系统"（第 1 讲）；
  3. 重构与分层（DW + Data Mart）：业务系统底层数据结构不适合做复杂分析，需要专门的数据架构。

它还暗含一个判断标准：当"整合"的成本高于"分立"的成本时，就分立（第⑤阶段 OCRM 独立开发）。这和"高内聚低耦合"是同一个判断——边界清晰比功能齐全更重要。

补第 ④ 阶段讲的三个难点特别真实：ERP 和 CRM 各有报表模块但数据孤立；业务系统的数据结构不适合多维分析；经营指标统计口径太多导致管理混乱。这正是"数据仓库为什么存在"的标准答案。

第 5 讲 小结

一句话串起整讲：分析的活是把"文字写成的需求"翻译成"三张互相印证的图"——对象模型说清有哪些东西，动态模型说清它们按什么顺序动，功能模型说清数据怎么流；三张图对得上，需求才算被真正理解。

核心结论清单

  1. 分析要解决初步需求的五个毛病：不具体、不清晰、关系不明、有潜在缺陷、不分优先级。
  2. 三个视角：用例（功能）、结构（静态）、行为（动态）。
  3. 类图六关系强弱：泛化 = 实现 > 组合 > 聚合 > 关联 > 依赖；组合同生共死，聚合可分离，依赖只用于局部/参数。
  4. 状态图三标准事件：entry（进入时一次）、exit（退出时一次）、do（状态期间持续）。
  5. 活动图强调"活动到活动"的控制流，交互图强调"对象到对象"。
  6. 顺序图纵轴是时间、横轴是对象；协作图按空间结构布图；二者信息等价。
  7. 对象模型最核心；功能模型指出"发生了什么"，动态模型确定"什么时候发生"，对象模型确定"发生的客体"。
  8. 对象模型五层次：主题、结构、类&对象、属性、服务（主题层对应 7±2 原则）。
  9. 找类两把钥匙：客观事物五类 + 名词动词法；筛类五标准：冗余、不相干、模糊、属性、操作。
  10. 链属性应升格为类（借阅日期 → 借阅记录）。
  11. 继承可以自底向上（归纳）也可以自顶向下（演绎），通常要迭代几轮。
  12. 从脚本到事件跟踪图，再到状态图，最后从事件导出服务——方法是被事件"逼"出来的。

自测

1. 需求陈述里有一句"顾客可以退货，退货时需要记录退货原因和经手人"。用名词动词法分析，哪些词是候选类、哪些是属性、哪些是服务？

答案

名词候选类：顾客、退货（事件，应建类）。形容词/修饰性名词（作为属性线索）：退货原因、经手人——这两个应作为"退货"类的属性，而不是独立的类（除非系统还要管理经手人的权限、业绩，那时"经手人"升格为类）。动词候选服务：退货（顾客发起的行为）、记录（系统行为）。结论：新增"退货"类，属性为退货原因、经手人、退货时间、关联到原订单；服务为"创建退货单""审核退货"。

2. 为什么说"链属性"（如借书日期）不应该放在两端的类里？

答案

因为借书日期既不属于"学生"（一个学生有多次借阅，哪个日期算他的？），也不属于"书"（一本书被多人借过，同样说不清），它只属于"这一次借阅关系"。放在任一端都会导致：①同一个学生第二次借书时，前一次的日期被覆盖；②无法保留历史。正确做法是把这条关联升格为类（借阅记录），日期成为它的属性，它同时关联学生和书。判据：如果一个属性只在"某两个对象发生关系时"才存在，它就是链属性。

3. 状态图里 entry 和 do 有什么区别？用电梯例子说明。

答案

entry 是进入该状态时执行一次的动作；do 是处于该状态期间持续执行的动作。电梯例子：进入"Moving up"状态时 entry 可能做"关门、启动电机"（只做一次），而 do/moving to floor 表示在整个上行过程中持续检测楼层位置。同理，Idle 状态的 do/increase timer 表示空闲期间计时器一直在增长，涨到 [timer=time-out] 就触发去一楼的迁移。一句话：entry 是"进门那一下"，do 是"待在屋里一直做的事"。

4. 功能模型"没有增加新的信息"，那为什么还要建？请举一个它能发现的问题。

答案

它的作用不是产生新信息，而是独立视角的交叉校验。因为数据流图强制你画出"每个处理框的输入从哪来、输出到哪去"，所以能暴露另两个模型掩盖的漏洞。典型发现：①某个输出数据没有任何处理框产生（说明对象模型漏了一个类或服务）；②某个输入数据进来后没有处理框使用（说明这个需求其实没实现）；③某个处理框没有任何输入却产生输出（不可能实现的需求）。ATM 例中，正是靠对照 DFD 才确认分行对象应提供"验卡"而非"验证卡号"这个服务名。

5. 从"小门店用 Excel"到"集团用 DW + BI"，这个案例说明软件演化的什么规律？

答案

说明软件演化是跟着组织和业务规模走的，而且方向是"从单体走向系统之系统"。具体三层规律：①规模突破工具能力上限时必须换形态（Excel 无法支撑多人并发录入与一致性）；②单一系统无法覆盖全部业务时走向多系统联盟（ERP + CRM + OA + HRM），此时关键是边界清晰、接口明确；③当"分析型需求"与"交易型需求"冲突时，要分立数据架构（业务系统底层结构不适合多维分析，所以要 DW + Data Mart）。这与第 1 讲"软件形态从单一系统到系统之系统、从封闭到开放"完全一致。
