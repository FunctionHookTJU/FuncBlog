### 3.1 面向对象设计方法学：精化，不是翻译

课件第 52 页的定义值得逐字读：

> 针对面向对象需求分析所得到的软件需求模型（如用例图、交互图、分析类图），对其进行**不断精化（而非转换）**，获得软件系统的各类设计元素，如子系统、构件、设计类等，产生不同视角、不同抽象层次的软件设计模型，如软件体系结构图、用例设计交互图、设计类图、活动图等，形成软件系统完整和详尽的设计方案。

【补】**"精化（refinement）而非转换（transformation）"这四个字是 OO 设计的关键区别**。结构化方法里，分析模型（数据流图）和设计模型（结构图）是**两套完全不同**的表示，要靠人工"转换"，转换过程容易丢信息、出偏差——第 5 讲提到的"结构化分析技术存在一个致命的弱点：分析模型和设计模型之间存在本质性的断层"说的就是这件事。而 OO 方法里，分析类图和设计类图**用的是同一套概念**（类、属性、操作、关联），设计只是把分析模型"加细节"：加接口、加可见性、加具体的数据类型、加辅助类。**没有断层，所以不容易丢东西。**

### 3.2 面向对象设计的过程

课件第 54 页给的流程：

```
软件体系结构设计 → 用户界面设计 → 构件/子系统设计 → 用例设计 → 数据设计 → 类设计
                            （详细设计）
```

贯穿全程的支撑是"面向对象的概念、机制和建模语言"。

**典型的面向对象设计模型**（PPT 第 55 页）由四个部分组成，这和第 5 讲对象模型的五个层次是对应的：

```
问题域部分     人机交互部分
任务管理部分   数据管理部分
```

| 子系统 | 职责 |
|---|---|
| **问题域子系统** | 存放从分析模型直接来的领域类（ATM、账户、储户……） |
| **人机交互子系统** | 界面类，负责输入输出 |
| **任务管理子系统** | 并发、进程/线程、事件驱动 |
| **数据管理子系统** | 持久化：选存储方式、设计数据格式与相应服务 |

#### 3.2.2 设计问题域子系统（PPT 第 92–93 页）

五个动作：①调整需求；②**重用已有的类**；③把问题域类组合在一起；④增添一般化类以建立协议；⑤映射到具体结构（ATM 例）。

【补】**"重用已有的类"排在第二位，很说明问题**：设计阶段第一件该想的事不是"我要写什么"，而是"我手上有什么"。这和敏捷里"不要重复造轮子"、第 1 讲讲开源重用是同一个逻辑。

#### 3.2.3 设计人机交互子系统（PPT 第 94–95 页）

**界面设计七准则**（课件原文）：一致性、减少步骤、及时提供反馈信息、提供撤消命令、无须记忆、易学、富有吸引力。

**设计策略**：

- **分类用户**：按技能水平（初/中/高级）、按职务（总经理/部门经理/职员）、按工作性质（行政/技术）、按专业知识（外专业/专业/系统员）；
- **描述用户**：用户类型、特征（年龄、性别、受教育程度、限制因素）、关键成功因素（需求、爱好、习惯）、技能水平、完成本职工作的脚本；
- **设计命令层次**：研究现有交互含义与准则 → 确定初始命令层次 → 精化命令层次；
- **设计人机交互类**：用交互图表示界面之间的关系。

#### 3.2.4 设计任务管理子系统（PPT 第 119 页）

**先分析并发性**：通过 OOA 建立的动态模型判断——**如果两个对象彼此之间不存在交互，或它们同时接受事件，则这两个对象在本质上是并发的**。

然后设计任务：确定事件驱动型任务、时钟驱动型任务、优先任务、关键任务、协调任务；**尽量减少任务数**；确定资源需求。

#### 3.2.5 设计数据管理子系统（PPT 第 120 页）

数据管理子系统是"系统存储或检索对象的基本设施"，它建立在某种数据存储管理系统之上，**并隔离了数据存储管理模式的影响**。

两个设计步骤：

1. **选择数据存储管理模式**：文件管理系统 / 关系数据库管理系统 / 面向对象数据库管理系统；
2. **设计数据格式 + 设计相应的服务**（针对所选模式）。

【补】**"隔离存储模式的影响"这句话是这一页的精华**：它意味着问题域的对象不应该知道数据存在 MySQL 还是文件里，中间要有一层负责转换（这就是后来"数据访问层/Repository 模式"的雏形）。**换数据库时只改这一层，上层不动**——这是第 6 讲"信息隐藏"原则在架构上的直接应用。

### 3.2.1 架构与设计模式：三层抽象

课件第 56–59 页给了两个关键定义：

**软件体系结构（Software Architecture，SA）**，也称软件架构：**从高层抽象角度刻画组成软件系统的设计元素及它们之间的逻辑关联。**

**软件设计模式**：以设计重用为目的，采用一种良定义的、正规的、一致的方式记录的软件设计经验；关注在一般或特定设计环境中可能重复出现的设计问题，并给出经过充分实践考验的解决方案。它的要素有五项：**名称、问题、施用和约束条件、解决方案、效果**。

**三层抽象**（PPT 第 58 页），这是理解"模式"这个词的关键：

| 层次 | 面向 | 例子 |
|---|---|---|
| **体系结构风格** | 整个软件系统 | 分层、管道与过滤器、黑板、MVC、SOA、总线 |
| **构件设计模式** | 子系统或构件 | （中间层模式） |
| **实现设计模式** | 构件中某个特定问题 | 23 种 GoF 模式（工厂、单例、观察者……） |

【补】**这三层的关系可以这样理解**：架构风格是"城市的规划"（路怎么走、区分几个片区），构件模式是"小区的设计"（楼怎么排），实现模式是"户型的装修"（房间怎么分隔）。**越往上越影响全局，越往下越影响局部**。第 7 讲会详细展开六种架构风格和 23 种设计模式的分类。

### 3.3 面向对象设计的四项优势

课件第 121 页给了四条，每条都有实际含义：

| 优势 | 含义 |
|---|---|
| **高层抽象和自然过渡** | OO 概念贴近现实，减少工程师与用户的交流鸿沟，支持大型复杂系统开发 |
| **多种形式和粗粒度的软件重用** | 封装、接口、继承、多态都支持重用；重用的粒度可以是类、构件、框架 |
| **系统化的软件设计** | 系统性支持架构设计、界面设计、数据设计、构件设计、子系统设计、用例设计、类设计 |
| **支持软件的扩展和变更** | 接口、抽象类、继承、实现等机制，可设计出易于扩展变更的模型 |

【补】**第 2 条"粗粒度重用"值得展开**：结构化方法的重用单位是**函数**（十几行），OO 的重用单位可以到**类**（几百行）、**构件**（几千行）、**框架**（几万行，如 Spring）。粒度越来越大，是因为封装把"一堆相关的函数和数据"打成了一个可整体搬走的包裹。这也呼应第 2 讲"重用粒度越来越大"的发展规律。

### 4 设计输出、文档、缺陷与评审

**输出两件套**（PPT 第 123 页）：

- **软件设计模型**：从多视角、多抽象层次描述设计信息，用 UML、模块图、层次图等图形化方式刻画；
- **软件设计文档**：用自然语言结合模型，详细描述架构设计、子系统与构件设计、界面设计、用例设计、数据设计等。

**设计文档规范**（PPT 第 124 页）的章节结构：文档概述 → 系统概述 → 设计目标和原则 → 设计约束与现实限制 → 体系结构设计 → 用户界面设计 → 子系统/构件设计 → 用例设计 → 类设计 → 数据设计 → 接口设计。

【补】**注意"设计目标和原则"这一章**——它要求设计师**把自己的取舍写下来**："为了性能牺牲了一层抽象""为了兼容旧接口保留了一个冗余字段"。这一章是给三年后的维护者看的，也是最有价值的一章，但最常被跳过。

**四类设计缺陷**（PPT 第 125 页）：

| 缺陷 | 表现 |
|---|---|
| **设计未能满足需求** | 对需求理解有偏差，设计的软件无法满足用户需要 |
| **设计质量低下** | 未遵循设计原则、缺乏经验，导致不易维护和扩展 |
| **设计存在不一致** | 不同设计制品对同一设计有不同描述，或要素之间不一致、冲突 |
| **设计不够详尽** | 没提供细节，程序员无法据此编码 |

**评审要点**（PPT 第 126 页）：

- **谁参与**：程序员、测试工程师、用户、质量保证人员、设计工程师；
- **评什么**：文档规范性（是否符合设计规格说明书）、可理解性、合法性（是否符合标准法规）、质量水平（是否遵循设计原则）、是否满足需求、优化性（还有没有可优化的地方）。

【补】**把"程序员"列为评审人是很聪明的一招**：因为程序员是设计的**第一消费者**，如果程序员看不懂设计、或者看完还得再问十遍，那这份设计就是不详尽的。**让下游用户参与评审上游产物，是保证"信息传递不丢"的最有效手段。**

**设计管理**（PPT 第 127 页）：变更管理（哪些变了、反映在哪、版本怎么变）、追溯管理（什么原因导致变更、评估影响域）、**基线管理**（通过评审后纳入基线库）。

### 第 6 讲 小结

**一句话串起整讲**：设计是在需求的约束下给出"实现方案"，它的核心动作是"分解 + 隐藏"，它的评价标准是"高内聚低耦合"，它的成败取决于是否遵守了那七条原则。

**核心结论清单**

1. 设计 = 需求 + 制约因素 → 解决方案；没有约束就不需要设计。
2. 设计处于承上启下的位置，设计质量直接决定产品好坏。
3. 好设计要内外兼修：高可靠、高效率、高可理解、高可维护——四者经常冲突，要权衡。
4. 设计过程四步：架构（最贵）→ 界面 → 详细（最便宜）→ 文档与评审，全程迭代。
5. 七条原则：抽象与逐步求精、模块化、信息隐藏、关注点分离、软件重用、迭代设计、可追踪性。
6. **软件工程基本定理**：C(P1+P2) > C(P1)+C(P2)，所以分解能降低复杂度。
7. 但分解有最优区间：模块成本随数量线性上升，接口开销近似平方上升，中间存在最小成本区域。
8. 内聚七级（低→高）：偶然、逻辑、时间、过程、通信、顺序、功能。
9. 耦合七级（高→低）：内容、公共、外部、控制、标记、数据、非直接。
10. 前三类耦合是"共享存储"式，从控制耦合起是"接口调用"式。
11. OO 设计是"精化"而非"转换"，没有结构化方法的模型断层。
12. OO 设计模型四部分：问题域、人机交互、任务管理、数据管理。

### 自测

**1.** 判断下面这个模块的内聚等级，并说明理由：

```
void processOrder() {
    // 1. 校验订单合法性
    // 2. 计算总价（用校验后的订单）
    // 3. 生成出库单（用总价）
    // 4. 打印日志
}
```

<details><summary>答案</summary>

**顺序内聚（第 6 级）**，接近功能内聚。理由：四个步骤都与"处理订单"这一功能相关，且**按顺序执行、前一步的输出是后一步的输入**（校验后的订单 → 总价 → 出库单），符合"顺序内聚"的定义。之所以不判为"功能内聚"：功能内聚要求所有成分**共同完成一个单一功能**，而这里实际做了"校验 + 计价 + 出库 + 日志"四件可分别命名的事，理论上可以再拆。如果第 4 步"打印日志"与其他三步无关（只是顺手加的），那这一部分会把整体拉向"时间内聚"。**评分关键：说清"有数据顺序依赖 → 顺序内聚"，并指出可再细化的点。**

</details>

**2.** 有两个模块，A 把整个 `Student` 对象传给 B，B 只用了其中的 `name` 字段。这是哪种耦合？怎么改进？

<details><summary>答案</summary>

**标记耦合（特征耦合）**——传递的是数据结构而不是简单数据项。问题在于 B 与 `Student` 的**完整结构**耦合了：以后 `Student` 加字段、改字段类型、甚至改类名，B 都可能被牵连（因为它拿到了整个对象，编译器无法判断它到底用了什么）。改进：**只传 `name` 字符串**，降为**数据耦合**。这条改进的本质是第 6 讲的原则"模块间仅交换完成功能所必需交换的信息"（信息隐藏）。

</details>

**3.** 为什么"内容耦合"比"公共耦合"更糟？请从"能不能被发现"的角度解释。

<details><summary>答案</summary>

因为内容耦合**在接口上完全看不出来**。公共耦合虽然也危险（改全局数据结构会影响所有使用者），但至少"使用了全局变量"这件事是显式的，搜一下全局变量名就能找到所有依赖点。而内容耦合是一个模块**直接读写另一个模块的内部数据、甚至跳进对方内部执行**，这种依赖不会出现在任何函数签名里，只能靠通读代码发现。一旦对方改了内部实现，你这边会莫名其妙地崩，而且**编译器不会报错**。所以耦合等级的排序本质上是"**依赖的可见性**"排序：越不可见越危险。

</details>

**4.** 老师让你"把系统拆成 30 个微服务，这样最灵活"。用软件工程基本定理和成本曲线反驳他。

<details><summary>答案</summary>

要点三条：①**基本定理只说"分开解决比合起来省"**，它保证的是"分解有收益"，没说"越分解越省"；②成本曲线显示：模块自身成本随数量**线性上升**，接口开销随数量**近似平方上升**，总成本是 U 型，存在**最小成本区域**；③30 个服务意味着至少几十条跨服务调用链、几十套部署与监控、版本兼容与分布式事务问题，**接口开销极可能超过分解收益**。判断标准不是"数量"，而是"**每个模块是否还能被一个人在一周内完整理解**"。合理的反问是：这 30 个服务的边界，是按业务能力划的，还是按"技术分层"硬切的？

</details>

**5.** 为什么说 OO 设计的"精化"比结构化方法的"转换"更不容易丢信息？

<details><summary>答案</summary>

因为**表示体系是否连续**。结构化方法里，分析用数据流图（数据在加工之间流动），设计用结构图（模块调用层次），二者概念体系不同，转换需要人工判断"哪个加工变成哪个模块""哪些数据流变成接口参数"，每一步都可能丢信息或引入偏差——这就是课件所说的"分析模型和设计模型之间的本质性断层"。OO 方法里，分析类图和设计类图用的是同一套元素（类、属性、操作、关联），设计只是在**同一个模型上增加细节**（可见性、类型、接口、辅助类、子系统划分），不需要换一套语言重画，因此**信息天然连续**，且可以通过"可追踪性"逐条核对。

</details>
