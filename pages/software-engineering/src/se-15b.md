### 3.1 分析和确定需求优先级

课件第 103 页给出分析过程四步闭环：

```
初步软件需求
   → 分析和确定软件需求优先级 → 软件需求优先级列表
   → 分析和建立软件需求模型   → 软件需求模型
   → 文档化软件需求           → 软件需求文档
   → 确认和验证软件需求       → 确认后的模型和文档
   （↑ 迭代）
```

**为什么要分重要性？** 因为"从用户和客户的视角，软件需求的重要性是不一样的"（PPT 第 105 页）：

- **核心需求**：在解决问题方面起**举足轻重**的作用，提供了软件系统所特有的功能和服务，**体现了系统的特色和优势**；
- **外围需求**：提供次要、辅助性的功能和服务。

以"空巢老人看护软件"为例（PPT 第 106 页）：

| 用例 | 标识 | 重要性 |
|---|---|---|
| 监视老人 / 自主跟随 / 获取老人信息 / 检测异常 / 通知异常 | UC-MonitorElder 等 | **核心** |
| 控制机器人 / 音视频交互 / 提醒服务 / 用户登录 / 系统设置 | UC-ControlRobot 等 | 外围 |

【补】**这张表的重点不是结论，而是排序逻辑**：凡是"没有它这个系统就不成立"的，是核心（比如摔倒检测——没有它，机器人就只是个摄像头）；凡是"所有系统都有的"，是外围（登录、设置）。**核心需求决定这个软件为什么存在，外围需求决定它好不好用。**

**优先级怎么定**（PPT 第 107 页）：用户对实现顺序的要求也不一样，有些要尽早交付以发挥价值，有些可以滞后。考虑因素：

- 结合项目具体约束（进度、人力），确保整个迭代开发中**有计划、有重点**地实现；
- 按需求的**重要性**定优先级；
- 按用户的**实际需要**定优先级。

【补】**重要性和优先级不是一回事**，这是常考的辨析点：**重要性是"这个需求对系统有多关键"，优先级是"这次先做哪个"**。一个核心需求可能因为依赖外部接口而下期做（优先级低），一个外围需求可能因为能立刻上线产生收益而先做（优先级高）。课件把两者分开讲，就是因为现实中经常冲突。

### 3.2 分析和建立需求模型：理解、表达、验证

课件第 109 页把分析工作归成三项，这三项恰好对应"想明白—写下来—检查对"：

| 内容 | 做什么 |
|---|---|
| **理解** | 系统分析员、用户、领域专家交流，理解用户需求与关键知识背景 |
| **表达** | 形成文档资料（由**对象模型、动态模型、功能模型**组成） |
| **验证** | 因问题复杂、人与人的交流有随意性和非形式化特点，一次理解很难到位，须进一步验证需求的正确性、完整性和有效性 |

【补】**"表达"那一条把第 5 讲提前点名了**：面向对象分析的三大模型就是这里的"表达"产物。所以第 4 讲和第 5 讲不是两门课，而是"需求的收集与界定"和"需求的建模与精化"两个阶段。

### 3.3 需求工程的输出：三件套

| 输出 | 形态 | 承载什么 |
|---|---|---|
| **软件原型** | 可运行软件 | 直观展示业务流程、操作界面、输入输出等功能性需求信息 |
| **软件需求模型** | 可视化图形 | 从多个视角描述功能需求：**用例模型、用例的交互模型、分析类模型、状态模型**等 |
| **软件需求文档** | 图文并茂 | 结合模型与自然语言，详尽刻画功能性与非功能性需求、需求优先级列表 |

**需求文档模板**（PPT 第 111 页）——注意课件排版的顺序有误，我按逻辑重排：

| 章 | 内容 |
|---|---|
| 1 引言 | 编写目标、读者对象、文档概述、术语定义、参考文献 |
| 2 软件系统概述 | 产品概述、用户特征、设计和实现约束、假设与依赖 |
| 3 功能性需求描述 | 功能概述、**用例模型**、**分析模型** |
| 4 非功能性需求 | 质量属性等 |
| 5 界面需求 | 界面要求 |
| 6 接口定义 | 外部接口 |
| 7 进度要求 | |
| 8 交付要求 | |
| 9 交付形式 | |
| 10 验收要求 | |

【勘误】课件第 111 页把"4 非功能性需求"到"10 验收要求"排在"3 功能性需求描述"之前，第 3 章被挤到最后，属于排版错位；按文档逻辑应为 1→2→3→4…→10。

【补】**"软件需求模型是文档中的重要组成成分"**——这句话是这一页的落款。它意味着文档不能只有文字，也不能只有图，**必须是"图 + 文字"的双轨**：图负责结构与关系，文字负责细节与例外。

**撰写六条注意事项**（PPT 第 112 页）：遵循规范；图文并茂；完整表述（功能 + 非功能）；共同参与（工程师与用户、客户一起写）；语言简练；**前后一致**（同一需求的表述不能自相矛盾）。

### 3.4 需求评审

**评审四步**（PPT 第 113 页）：阅读和汇报需求制品 → 收集和整理问题 → 讨论和达成一致 → **纳入配置**。

**需求缺陷六种**（PPT 第 114 页），这份清单可以当"找茬清单"用：

1. **需求缺失**：漏掉了一些重要需求；
2. **描述不正确**：理解存在偏差；
3. **描述不准确**：表述与用户要求不一致；
4. **有冲突、不一致**；
5. **不可行**：存在可行性问题；
6. **不详尽**：没有提供足够详细的信息。

**评审要看十项**（PPT 第 115 页）：内容完整性、内容正确性、内容准确性、内容一致性、**内容多余性**（是不是都是用户期望的）、内容可追踪性、文档规范性、图符规范性（UML 用得对不对）、表述可读性、图表一致性（引用是否正确）。

【补】**"内容多余性"这一项很反直觉，但极重要**：多做的功能不是"送分"，是**负债**——它要设计、要编码、要测试、要维护，还不一定有人用。这就是后来"最小可行产品（MVP）"思想的雏形。

### 3.5 需求确认与验证：六个可行性

课件第 116 页给了六维可行性，比通常说的"技术经济可行"细得多：

| 维度 | 问什么 |
|---|---|
| **技术可行性** | 需要哪些技术？是否成熟？团队是否掌握关键技术？ |
| **设备可行性** | 需要哪些设备/系统？团队是否已具备？ |
| **进度可行性** | 用户提的进度要求，以现有的人力与技术水平能否达成？ |
| **成本可行性** | 在成本约束下能否做出满足需求的产品？ |
| **商业可行性** | 需求是否有商业价值？能否被市场和用户认可？投入能否获得预期收益？ |
| **社会可行性** | 是否违背社会道德、文化伦理、法律法规、行业标准？ |

【补】**"社会可行性"是这六条里最容易被学生忽略、但在真实项目里最容易致命的一条**：一个人脸识别考勤系统，技术上完全可行，但如果用于教室监控学生表情，就直接撞上隐私与伦理红线。第 1 讲把"隐私性（Privacy）"列入可信软件的四大要求，与此同源。

### 3.6 需求变更管理：三件事

课件第 117 页把变更管理拆成三层，正好对应第 2 讲的"双向追踪原则"：

| 管理 | 做什么 |
|---|---|
| **变更管理** | 明确哪些需求变了、反映在模型和文档的哪些部分、版本发生了什么变化 |
| **追溯管理** | **溯源**（谁提的、为什么改，判别合法性）+ **评估影响域**（会影响哪些制品）+ 评估对项目的影响 |
| **配置管理** | 形成**需求基线** |

【补】**"基线（baseline）"这个词要理解**：它是一条"冻结线"——通过评审的需求文档被纳入基线，之后任何改动都必须走变更流程，而不是"顺手改一下"。没有基线，需求文档就会变成一个大草稿，谁也不知道现在这一版算不算数。

### CASE 工具

课件第 118 页列了需求工程常用的五类工具：

- 文档撰写：Microsoft Office、WPS；
- 需求建模：Visio、Rational Rose、StarUML；
- 原型开发：Mockplus、Axure RP Pro、UIDesigner；
- 需求分析管理专用：IBM Rational RequisitePro；
- 配置管理：Git、GitHub、GitLab、PVCS、SourceSafe。

【补】**注意这里出现了"分类"这件事本身的价值**：写文档、画模型、做原型、管需求、管版本，是五种不同的活动，各有各的工具。**这也说明需求工程不是"一个动作"，而是一条工具链。**

### 第 4 讲 小结

**一句话串起整讲**：需求是"用户想要什么"到"工程师该做什么"之间的翻译，它天生隐晦、多源、易变，所以必须用工程手段（多种获取方法 + 建模 + 文档 + 评审 + 变更管理）把它逼成一份准确、一致、完整、可验证的契约。

**核心结论清单**

1. 需求有三个定位：价值所在、开发基础、验收依据。
2. 八条质量要求：有价值、正确、完整、无二义、可行、一致、可追踪、可验证。
3. 六个特点：隐式、隐晦、多源、易变、领域相关、价值不均——每一条都对应一种工程对策。
4. 三类需求：功能、质量（外/内）、约束。
5. 需求来源有六条通道，不只是"用户说"。
6. 六种获取方法：访谈会议、问卷、现场观摩、业务资料、原型、群体化。
7. 需求工程五环节闭环：获取 → 分析 → 确认验证 → 文档化 → 管理（迭代）。
8. 需求描述的三种手段各有边界：自然语言会二义，原型不细，UML 需要学习成本。
9. 用例图四要素：系统边界、执行者、用例、关系（关联/扩展/包含/泛化）。
10. 用例描述四字段：前置条件、基本路径、可选路径、后置条件。
11. 分析四步：定优先级 → 建模型 → 写文档 → 确认验证。
12. 可行性六维：技术、设备、进度、成本、商业、社会。

### 自测

**1.** 把这条需求改写成"无二义、可验证"的版本：「系统要快速响应用户的查询请求。」

<details><summary>答案</summary>

原句有三个二义点：多快算"快速"？什么样的"查询请求"？在什么负载下？改写示例：「在 200 个并发用户、数据库记录数不超过 100 万条的条件下，对按书名/作者/类别组合查询的请求，95% 的请求应在 1.5 秒内返回结果，全部请求不超过 3 秒。」要点是补齐**指标 + 条件 + 度量方式**三件事，这样它才能通过第 8 条质量要求"可验证"，也才能在第 9 讲直接变成一条性能测试用例。

</details>

**2.** 用例图中，`<<include>>` 和 `<<extend>>` 最容易混，请各举一例并说明判断依据。

<details><summary>答案</summary>

`<<include>>`：开户、存款、取款、转账都**必须**校验密码，所以"校验密码"被包含进这四个用例——被包含者每次都会执行。`<<extend>>`：自动售货机"买货"时，**有时候**顾客买的是散装饮料，需要额外的"购买散装饮料"流程，所以后者扩展前者——扩展者只在特定条件下插入。判断依据：**"是不是每次都要做"**。是 → include；"有时才做" → extend。另外 include 的箭头指向被包含用例，extend 的箭头指向被扩展（基础）用例，方向不要画反。

</details>

**3.** 为什么课件说"用例图把系统看成黑盒子"，这对需求阶段有什么好处？

<details><summary>答案</summary>

黑盒子意味着只描述"外部能看到什么"，不描述"内部怎么实现"。好处有三：①**用户能看懂并参与评审**——他们不懂技术但懂业务；②**不锁定实现方案**——同样的用例可以有多种设计与实现，需求阶段过早定实现会限制设计空间（第 6 讲的设计多样性）；③**划清了系统边界**——框内是我们要做的，框外是别人（或已有系统）的事，避免范围蔓延。代价是它不表达非功能需求、不表达时序细节，所以还需要用例描述、交互图来补。

</details>

**4.** 客户临时说"这个功能很急，先加上，文档回头再补"。按需求变更管理的三层，你应该做什么？

<details><summary>答案</summary>

按"变更—追溯—配置"三层处理：①**变更管理**：记录这是哪条需求变了、影响需求模型/文档的哪些部分、版本升到几；②**追溯管理**：先问**谁提的、为什么改、合不合法**（是不是真的客户决策，还是个别人的偏好），再评估**影响域**（要改哪些用例、哪些设计、哪些测试），最后评估对进度成本的影响；③**配置管理**：改动必须基于基线做，改完重新纳入基线。绝对不能"先做后补文档"——因为第 10 讲会告诉你，没进文档的改动就是将来维护时的黑洞，而且它一定会和别的需求冲突（一致性被破坏）。

</details>

**5.** 需求优先级和需求重要性有什么区别？举一个"核心需求优先级反而低"的例子。

<details><summary>答案</summary>

重要性是"这个需求对系统成立有多关键"（核心/外围），优先级是"这一轮先做哪个"。核心需求可能因为**前置条件不具备**而优先级低：例如空巢老人系统的"检测异常（摔倒识别）"是核心需求，但摔倒识别模型需要大量真实数据训练，第一期拿不到，于是第一期先做"监视 + 音视频交互"（外围），把摔倒检测放到第二期。这不是降级，而是**按依赖关系排期**——重要的东西不一定能先做。

</details>
