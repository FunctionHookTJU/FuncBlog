### 1.1–1.2 为什么"初步需求"还不够

课件第 3 页列了初步软件需求的五个毛病，这五条正好解释"为什么要有第 5 讲"：

| 问题 | 后果 |
|---|---|
| **不具体** | 没有提供细节性内容 |
| **不清晰** | 描述不够清晰、直观、详实 |
| **关系不明朗** | 没深入分析不同需求项之间的关系 |
| **存在潜在缺陷** | 潜在缺陷难以被发现 |
| **没有区分** | 没鉴别重要性差别、没区分开发优先级 |

于是软件分析的任务是：**基于初步需求，进一步精化和分析，确定优先级，建立需求模型，发现和解决缺陷，形成高质量的模型与需求规格说明书**。

【补】**这里有个容易混的地方，先说清楚**：第 4 讲是"**需求工程**"（把需求从人嘴里挖出来、写成文档），第 5 讲是"**软件分析**"（把需求精化成模型、检查一致性）。前者偏"沟通与记录"，后者偏"建模与推理"。课件的标题把它们分开，是有道理的。

### 1.3 三个视角

课件第 6 页把分析视角分成三类，这张表值得背（第 0 章已给过，这里补上"功能与行为的本质区别"）：

| 视角 | 问什么 | 用什么图 |
|---|---|---|
| **用例视角** | 具有哪些功能、功能间有何关系、功能与利益相关方有何关系 | 用例图 |
| **行为视角** | 用例是如何通过业务领域中一组对象及它们间的交互来达成的 | 交互图（顺序/协作）、状态图、活动图 |
| **结构视角** | 业务领域有哪些重要概念，它们之间有什么关系 | 类图（概念模型） |

课件在这一页留了一个思考题："**功能和行为有何本质性的区别？**"

【补】**我的回答**：功能回答"**系统能做什么**"（外部可见的能力，静态清单）；行为回答"**系统怎么做成那件事**"（内部对象按时间顺序的协作，动态过程）。同一个功能可以有很多种行为实现——"取款"这个功能不变，但用 ATM 自助还是柜台办理，行为完全不同。所以**功能是"什么"，行为是"怎么"，结构是"谁"**。

### 类图（结构视角的主角）

课件第 8 页拆解了一个类框的三部分：**类名 / 属性 / 操作**。

```
        Order
  -id: integer
  -quantity: integer = 0
  +Order(id: integer)
  +getQuantity(): integer
  +setQuantity(id: integer)
```

读法要点：

- `-` 表示 private，`+` 表示 public，`#` 表示 protected；
- 属性写法是 `可见性 名称: 类型 = 默认值`；
- 操作写法是 `可见性 名称(参数: 类型): 返回类型`；
- 还可以加构造型（`<<Constructor>>`、`<<accessor>>`、`<<mutator>>`、`<<business logic>>`）说明方法职责。

**六种关系的强弱排序**（PPT 第 9–16 页，第 0 章已给符号，这里补上**代码体现**，考试常问"这段代码是哪种关系"）：

| 关系 | 强弱 | 代码体现 | 一句话 |
|---|---|---|---|
| 泛化 | 最强 | `extends` | is-a |
| 实现 | = 泛化 | `implements` | 类实现接口 |
| 组合 | 次强 | 成员变量，**整体负责创建销毁部分** | 同生共死 |
| 聚合 | 中 | 成员变量，部分可独立存在 | 可分离的整体-部分 |
| 关联 | 弱 | 成员变量 | 一个类知道另一个 |
| 依赖 | 最弱 | **局部变量、方法参数、静态方法调用** | 临时用一下 |

【补】**用"生命周期"一眼区分组合与聚合，用"作用域"一眼区分关联与依赖**：

- 组合：`class Company { private List<Department> depts = new ArrayList<>(); }` —— 部门在构造时创建，公司没了部门也没了。
- 聚合：`class Car { private List<Tire> tires; }` —— 轮胎从外面传进来，车报废轮胎还能用。
- 关联：`class Teacher { private List<Student> students; }` —— 学生是长期持有的字段。
- 依赖：`class Report { void print(Printer p) { p.output(); } }` —— `p` 只是参数，方法结束就没了。

### 对象图与包图

**对象图**（PPT 第 18 页）：可以看作**类图的实例**，帮助理解复杂的类图。表示形式与类图几乎相同，**主要差别是对象名下面要加一条下划线**；对象名首字母小写；通常只有名称和属性。

**包图**（PPT 第 19 页）：刻画包间的构成和依赖关系。包可以包含一组有逻辑关联的 UML 模型元素；包间关系有**构成关系**和**依赖关系**。

【补】**包图的价值在"分而治之"**：课件说它"以结构化、层次化方式组织管理大型软件模型，使得分别处理不同包的开发团队之间的相互干扰程度降至最低"。**这句话是包图存在的唯一理由**——如果只有一个团队，包图画不画都行；一旦有多个团队，包图就是"地盘划分协议"。

### 状态图

定义（PPT 第 21 页）：**由状态、变迁、事件和活动组成的状态机**，用来描述类的对象所有可能的状态以及事件发生时状态的转移条件。

基本符号：

| 符号 | 含义 |
|---|---|
| 实心圆 | 初始状态（**一个**） |
| 空心圆套实心圆 | 结束状态（**0 个或多个**） |
| 圆角矩形 | 状态（内含状态名、状态变量、活动） |
| 箭头 | 由事件导致的状态转换 |

**活动区里的三个标准事件**（PPT 第 22 页），这是最常考的点：

| 事件 | 时机 |
|---|---|
| **entry** | **进入**该状态时的特定动作 |
| **exit** | **退出**该状态时的特定动作 |
| **do** | **处于**该状态期间持续执行的动作 |

语法是：`event-name(参数表) [警戒条件] / 动作表达式`。例：`go up(floor) [timer=time-out] / start motor`。

**事件的四种类型**：消息型（同步，其他对象发来消息）、信号型（异步）、时间型（到达特定时间点）、条件型（属性取值满足条件）。

课件第 24 页用**电梯**举例，这个例子很经典：

```
Idle (timer=0, do/increase timer)
  ├─ go up(floor) ──→ Moving up (do/moving to floor) ──arrived──→ ...
  ├─ go down(floor) → Moving down (do/moving to floor)
  └─ [timer=time-out] ──→ Moving to First floor
```

【补】**注意 `do/increase timer` 这个写法**：电梯空闲时计时器一直在涨，涨到超时就自动回一楼。**`do` 事件的精髓就是"在这个状态里持续做的事"**，它不需要外部触发——这跟 `entry`（只做一次）区别很大，考试常考这个区别。

### 活动图

定义（PPT 第 25 页）：是**状态图的一种特殊情况**，这些状态大都处于**活动状态**。本质是流程图，描述**活动到活动的控制流**。

一句话区分交互图与活动图：

> 交互图强调的是**对象到对象**的控制流，活动图强调的是**活动到活动**的控制流。

两种增强画法：

- **带泳道的活动图**（PPT 第 26 页）：泳道表明每个活动由**哪些人或哪些部门**负责完成。这是活动图最实用的变体——一眼看出"谁在干什么、哪里要交接"。
- **带对象流的活动图**（PPT 第 27 页）：把涉及的对象放进图中，用**带箭头的虚线**连接到创建/修改/撤销它的活动上，表示对象流。

【补】**活动图 vs 流程图**：形式上几乎一样，区别在于活动图是 UML 的一部分，支持**并发（分叉/汇合）**、泳道、对象流；而流程图只有顺序分支循环。所以业务流程图常用活动图画，算法细节用流程图/NS 图画（第 7 讲）。

### 顺序图

定义（PPT 第 28–29 页）：交互图的一种，描述对象之间**消息发送的先后顺序**，强调**时间顺序**。主要用途是把用例表达的需求转化为更正式、更精细的表达——**用例常被细化为一个或多个顺序图**，同时它也能有效描述"如何分配各类的职责"。

要素：

| 要素 | 表示 |
|---|---|
| **纵向 = 时间轴** | 对象下方的**虚线**是生命线；生命线上的**长条矩形**是活跃期（执行期） |
| **横向 = 消息** | 对象顶部矩形框写对象名（可带下划线，表示是某类的实例） |
| 消息箭头 | 从上到下按时间顺序排列；**箭头形状表示消息类型** |

**五种消息**（PPT 第 30–31 页）：

| 类型 | 含义 | 画法要点 |
|---|---|---|
| **同步消息** | 发送者等待接收者处理完才继续 | 实心箭头 |
| **异步消息** | 发送完不等待，继续自己的处理 | 开叉箭头 |
| **自消息** | 对象发给自己的消息 | 折回自身的箭头 |
| **返回消息** | 处理完成，结果沿返回消息传回 | 虚线箭头 |
| **创建/销毁消息** | 消息传递目标对象的创建与删除 | 指向对象框 / 打叉 |

课件第 31 页用"叫吃饭"的类比讲同步异步（第 0 章已引），还给了**带时间延迟的消息**画法（标注 `时延小于10ms`）。

**组合片段**（PPT 第 32–33 页）：用来表达交互执行的条件与方式，常用四种：**抉择（alt）、选项（opt）、循环（loop）、并行（par）**。图中用左上角带标签的方框表示，方框内写警戒条件。

【补】**顺序图最容易画错的两个地方**：①**生命线不该画的太长**——对象没参与这段交互就不要画；②**返回消息常被省略**，但在强调"谁等谁"的场合必须画，否则看不出同步还是异步。

### 协作图（通信图）

定义（PPT 第 34 页）：交互图的一种，描述**收发消息的对象的组织关系**，强调对象之间的**合作关系**。

一句话记住区别：

> **顺序图按时间顺序布图，协作图按空间结构布图。**

消息标签语法：`前缀 守卫条件 序列表达式 [返回值 :=] 消息名`，例如 `1: [printer free] print(file)`。

### 构件图与部署图

**构件图**（PPT 第 39–40 页）：表示系统中构件与构件之间、类或接口与构件之间的关系。构件之间是**依赖关系**，类/接口与构件之间是**依赖或实现关系**。

构件的三种形态：

| 类型 | 含义 |
|---|---|
| **源构件** | 仅在编译时才有意义（如 `.java`） |
| **二进制构件** | 源构件的编译结果（如 `.class`、`.obj`） |
| **可执行构件** | 链接所有二进制构件得到的可执行程序文件 |

注意：**构件图只把构件显示成类型**；要显示实例必须用部署图。

**部署图**（PPT 第 43、47 页）：描述系统运行时进行处理的**节点**以及在节点上活动的**构件的配置**，强调物理设备及它们之间的连接关系。用途：描述系统如何部署、显示硬件中的软件与连接协议、平衡运行时计算资源分布、描述组织的硬件网络结构。

两个描述符号：

- **节点与连接**：节点用**立方体**表示（代表一个物理设备及在其上运行的软件系统）；节点间连线表示通信线路（UML 称"连接"）；通信类型用**构造型**标在连线旁，指定协议或网络类型（`<<HTTP>>`、`<<JDBC>>`、`<<Web Services>>`）。
- **构件与接口**：部署图中构件代表可执行的物理代码模块；接口用**一端是小圆圈的直线**表示。

**描述性 vs 实例性部署图**（PPT 第 49–50 页）：

- **描述性部署图**：节点写类型名（`Web服务器`、`应用服务器`、`数据库服务器`）；
- **实例性部署图**：节点名写成 `节点名: 类型名`（`1#服务器: Web服务器`、`3#小型机: 应用服务器`）。

【补】**这个区别和第 5 讲的"类 vs 对象"是同一个道理**：描述性部署图说"我们有两类机器"，实例性部署图说"这台机器上跑的是这个"。**画给客户看用描述性，画给运维看用实例性。**
