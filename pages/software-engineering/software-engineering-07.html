2–4 开源软件、软件质量与当代形态

2.1–2.3 闭源、开源与开源生态

闭源软件：代码不对用户开放，购买时只提供可运行软件或服务，以许可证（License）方式授权使用。课件第 27 页指出它的问题：无法掌握内部实现（是否存在安全漏洞、恶意代码），也无法修改完善，极大影响了开发者的创新自由。典型代表是 Windows、Office。

开源软件：源代码可以自由获取和传播，拥有者通过开源许可证赋予被许可人使用、修改、传播的权利。好处有三：源代码可自由传播、激发创作者热情、免费使用降低成本。

补"开源 ≠ 免费"这件事必须分清。 开源约束的是源代码的可得性与再分发权，不是价格。很多开源项目靠服务、托管、商业版本收费（如 MySQL 的双许可）。反过来，免费软件也可能是闭源的（如早期的 QQ）。考试如果出判断题"开源软件就是免费软件"，答案是错。

课件举的开源例子（PPT 第 29 页）：Linux、Ubuntu、Eclipse、Apache、JBoss、Tomcat、Kubernetes、MySQL、Firefox、TensorFlow、Apollo Auto、ONAP。

开源正在替代闭源（PPT 第 30 页）：服务器 OS 上 Linux/FreeBSD 替代 Unix；桌面 OS 上 Linux 系替代 Windows；数据库上 MySQL 逐渐代替 Oracle；浏览器上 Chrome/Firefox 占据第二第三；开发工具上 Eclipse 成为 Java 开发者首选 IDE。

补注意这里的表述是"逐步替代"而不是"全面替代"，课件给的是趋势判断而非事实结论。真实情况是分层替代：基础设施层（OS、数据库、Web 服务器）开源占优，办公与专业设计软件仍以闭源为主。

生态与数据（PPT 第 31–39 页）：2021 年 GitHub 上已有 2 亿多开源仓库；推动者包括政府（NASA 开源 200 多个项目、我国将开源列入十四五规划）、基金会（Apache、Linux、Eclipse、OSI）、企业（Google、Microsoft、IBM，以及华为、腾讯、阿里、百度）、个人（Linus Torvalds，GitHub 上有 6500 多万程序员）。《2015 开源软件年度调查》：78% 的公司基于开源运行、少于 3% 完全不用开源；64% 参与开源、超过 66% 优先考虑利用开源；89% 认为开源大幅提高创新速度。

四类平台的分工（PPT 第 34–37 页），这张表很容易被记混：

平台 定位
GitHub 全球最有影响力的开源软件托管平台
SourceForge 有影响力的开源开发平台和仓库，提供存储、协作、发布支持
Gitee 中国的开源托管平台（OpenHarmony、PaddlePaddle 等）
Stack Overflow 全球最大的软件开发知识分享/问答平台（不是托管平台）

补开源软件最实际的用法是"重用"：课件第 38 页举 Instagram——5 个工程师、十几款开源软件、8 周做出最初版本。结论是"重用和集成开源软件是快速搭建高质量系统的有效手段，能提高开发效率和质量"。

3 软件质量

课件第 41 页的定义很短：软件质量是指软件满足给定需求的程度，它是产品生命线。 页面上列的三个维度是可维护性、灵活性、可测试性。

补这个定义的关键在"给定需求"四个字：质量不是"越好越好"，而是"越符合需求越好"。一个跑得飞快但功能缺一半的系统，质量不合格；一个功能齐全但每次改都要一个月，质量也不合格。第 9 讲讲测试的"确认测试"，依据正是"软件需求规格说明书"——需求就是那把尺子。

课件第 42 页引了 2019 年华为的一号文件"全面提升软件工程能力与实践，打造可信的高质量产品"，把可信列为第一优先级，放在功能、特性和进度之上。可信的四条要求：

  • 安全性：抗击攻击，保护业务和数据的机密性、完整性、可用性；
  • 韧性（Resilience）：受攻击时仍保持良好运行状态，能快速恢复；
  • 隐私性（Privacy）：保护用户数据及隐私；
  • 可靠性和可用性：长期无故障运行，具备快速恢复和自我管理能力。

补"可信"和"质量"的关系：质量是"满足需求的程度"，可信是"在最坏情况下也敢用"。前者是常态下的评价，后者是异常态下的评价。这也是为什么它强调"放在功能和进度之上"——它是非功能需求里的最高优先级（第 4 讲会把这类需求归入"质量需求"）。

4 当代软件特征的变化

这一节是全章的"世界观"部分，课件从五个角度说软件变了。

4.1 地位和作用：软件已深入社会、经济、生活方方面面；作为创新工具改变各行业的解决问题方式（12306 改变购票、淘宝京东改变购物）；是实现行业信息化融合的使能技术；已成为人类社会的关键性基础设施，像电力、交通一样发挥基础性作用。

4.2 运行环境（PPT 第 45 页）：从大中小型机 → 基于 PC → 基于局域网分布 → 基于互联网 → 无处不在的计算。一句话总结：从"孤立、独立、局域、可控"到"分布、开放、动态、难控、无处不在"。

4.3 软件形态（PPT 第 46 页），五组"不是……而是……"，建议整段背：

不是 而是 含义
单一系统 系统之系统 由诸多系统联盟组合而成
纯技术系统 社会技术系统 + 生态系统 人、社会组织、物理设备、过程共同组成
同构系统 异构、多样的系统联盟 要素异构是客观必然
封闭环境 开放环境 环境与系统相互作用（互联网、战场）
封闭系统 动态适应系统 要素、关系、联盟持续变化，边界不明确

配套的三张图分别是：社会技术系统（人机物共生）、系统之系统（n 个子系统通过交互实现全局任务）、分布式异构系统（软件实体分散部署在互联网上，异构性是一种必然）、动态演化系统（智慧城市的多传感器协同）、生态系统（"运行"生态、"演化"生态、"人员"生态）。

补生态的定义值得单独记："共同环境 + 诸多要素 + 独立演化 + 相互依存"。它解释了为什么一个 App 的可用性不只取决于自己的代码——还取决于操作系统、云服务、第三方 SDK、网络运营商、甚至用户的手机型号。

4.4 规模（PPT 第 52 页），这组数字很适合当"量级感"训练：

系统 代码量
Windows XP / Vista / 7 3500 万 / 5000 万 / 7000 万行
宝马 7 系 超 2 亿行
特斯拉 Model S 超 4 亿行
空客 A380 超 10 亿行
F-35 约 800 万行，80% 的系统功能由软件实现

补看清一个反差：F-35 只有 800 万行，却"80% 的功能由软件实现"；而 A380 有 10 亿行。这说明代码量不是复杂度的唯一度量——同样的行数，实时性要求、安全性要求不同，复杂度天差地别。第 6 讲会给出"复杂度"更准确的理解：C(P1+P2) > C(P1)+C(P2)。

4.5 我国的挑战与使命（PPT 第 54 页）：桌面 OS 被 Windows 垄断、智能终端 OS 被 Google 垄断、工业软件和科学计算软件差距更大；整体实力不足，缺乏有国际影响力的软件企业和产品；需要加大加快国产化软件系统的研发和应用。课件用了八个字收尾："使命伟大，责任重大"。

第 1 讲 小结

一句话串起整讲：软件不是"一段能跑的程序"，而是"程序 + 数据 + 文档"三件套组成的、有生命周期的、会腐化也会被维护的逻辑产品；正因为如此，它必须被"工程化"地做出来。

核心结论清单

  1. 软件 = 程序 + 数据 + 文档，三者相互依存，合称软件制品。
  2. 文档的目的是阐述清楚、发现问题、开展交流、促进管理。
  3. 生命周期六阶段，每阶段回答一个问句、产出一批制品。
  4. 软件五特点：逻辑性、设计开发、易变性、复杂性、缺陷隐蔽性——每一条都直接推出一种工程手段。
  5. 软件分三类：应用、系统、支撑；数据库管理系统属于系统软件。
  6. 开源 ≠ 免费；开源的价值在"可获取、可修改、可重用"。
  7. 可信 = 安全 + 韧性 + 隐私 + 可靠可用，优先级高于功能与进度。
  8. 当代软件：基础设施化、开放化、系统之系统、社会技术化、规模爆炸。

自测

1. "软件不会磨损和老化"这句话对吗？为什么第 10 讲还要讲"软件老化"？

答案

对，但要理解它的限定。软件的物理层面不会磨损：跑一百万次和执行一次完全一样，没有材料疲劳。但软件的逻辑层面会老化：一次次修改让结构越来越乱、文档与代码越来越不一致、变更成本越来越高，表现为用户满意度下降、质量下降、成本上升——这就是第 10 讲的"逻辑老化"。所以准确表述是：软件没有物理老化，但有逻辑老化。

2. 一个团队说"我们的软件没有文档，但代码注释写得很全，所以不需要文档"。这句话错在哪？

答案

错在混淆了"代码级说明"和"制品级文档"。注释只能解释"这行代码在干什么"，无法承担文档的四项职能：定义和理解软件（整体需求与设计意图）、记录阶段性成果（为什么这样设计、放弃了哪些方案）、辅助不同角色交流（测试人员、运维、用户要看的是需求和操作说明）、促进管理（版本、变更、基线）。第 10 讲会补一刀：维护时 50%–90% 的时间花在理解程序上，而注释量再大也回答不了"这个需求当初为什么这么定"。

3. 为什么"缺陷的隐蔽性"会直接推出"必须做测试"这个结论？难道不能靠仔细写代码避免吗？

答案

不能。因为人一定会犯错（第 2 讲第 12 页："人总是会犯错误的"），而且缺陷来源不止编码——需求理解偏差、设计遗漏、接口不匹配都会带到代码里。缺陷隐蔽是因为它藏在逻辑里，不像硬件那样有物理征兆：数组越界可能只在某个特定输入组合下才崩。既然无法靠"仔细"消灭，就只能靠"运行"暴露——这正是第 9 讲软件测试的定义：通过运行程序来发现缺陷。

4. 判断：数据库管理系统、Eclipse、微信分别属于哪一类软件？

答案

数据库管理系统 → 系统软件（管理计算机资源，为应用提供基础设施）；Eclipse → 支撑软件（辅助开发）；微信 → 应用软件（面向特定应用领域）。判断口诀：离硬件近、管资源的是系统软件；帮人写软件的是支撑软件；解决具体业务问题的是应用软件。

5. 华为把"可信"放在功能、特性和进度之上，这个排序在工程上意味着什么？

答案

意味着当"多做一个功能"和"保证安全/可靠"冲突时，后者优先——即非功能需求具有一票否决权。工程后果是：需求阶段就要把安全性、韧性、隐私、可靠可用写成可验证的指标（第 4 讲的"质量需求"），设计阶段要专门设计（第 6、7 讲的架构风格选择），测试阶段要有专项测试（第 9 讲的非功能测试：性能、安全、可靠性、恢复测试）。如果等到上线前才想起可信，代价就是重做架构。
