算法 3：银行的四个步骤（PPT 第 13 页）

课件第 13 页先列银行的动作，再列商家的收条动作。先看银行。

第 (1) 步：自己算支付摘要。

H(EB(PI))=PIMDH\big(E_{B}(\mathrm{PI})\big)=\mathrm{PIMD}H(EB​(PI))=PIMD

翻译成人话：银行收到的是支付指令的密文 EB(PI)E_{B}(\mathrm{PI})EB​(PI)，它用自己的方式算一遍摘要，就得到了 PIMD\mathrm{PIMD}PIMD。注意这一步和商家第 (1) 步完全对称：商家自己算 GSOMD\mathrm{GSOMD}GSOMD，银行自己算 PIMD\mathrm{PIMD}PIMD——各人算各自手里那份的摘要。

第 (2) 步：验签。

H(H(EB(PI)) ∥ GSOMD)=?EC(DS)H\Big(H\big(E_{B}(\mathrm{PI})\big)\,\big\|\,\mathrm{GSOMD}\Big)\quad\overset{?}{=}\quad E_{C}(\mathrm{DS})H(H(EB​(PI))​GSOMD)=?EC​(DS)

翻译成人话：右边是「用持卡人的公钥把双重签名还原成总摘要 POMD\mathrm{POMD}POMD」；左边是「银行用自己算出的 PIMD\mathrm{PIMD}PIMD、加上商家转来的 GSOMD\mathrm{GSOMD}GSOMD，按 PIMD\mathrm{PIMD}PIMD 在前、GSOMD\mathrm{GSOMD}GSOMD 在后的顺序拼接再求摘要」。两边相等，就说明这个签名确实同时覆盖了这份定单和这份支付指令，银行确认了持卡人的签名。 课件原文的表述是「如果它们相等，则银行认证了持卡人的签名」。

把商家和银行的验签等式并排放，对称性一目了然：

商家 M 的验签 银行 B 的验签
自己算出的那一半 H(EM(GSO))=GSOMDH(E_{M}(\mathrm{GSO}))=\mathrm{GSOMD}H(EM​(GSO))=GSOMD H(EB(PI))=PIMDH(E_{B}(\mathrm{PI}))=\mathrm{PIMD}H(EB​(PI))=PIMD
别人转来的那一半 PIMD\mathrm{PIMD}PIMD（C 直接发来） GSOMD\mathrm{GSOMD}GSOMD（M 转发）
验证等式 EC(DS)=H(PIMD∥H(EM(GSO)))E_{C}(\mathrm{DS})=H(\mathrm{PIMD}\|H(E_{M}(\mathrm{GSO})))EC​(DS)=H(PIMD∥H(EM​(GSO))) EC(DS)=H(H(EB(PI))∥GSOMD)E_{C}(\mathrm{DS})=H(H(E_{B}(\mathrm{PI}))\|\mathrm{GSOMD})EC​(DS)=H(H(EB​(PI))∥GSOMD)

补这张表就是双重签名的「全部秘密」：一个签名只有一个「正确答案」POMD\mathrm{POMD}POMD，但通向它的路有两条——商家走「自己的定单 + 收到的支付摘要」，银行走「自己的支付指令 + 收到的定单摘要」。两条路都不需要看到对方的全文。设计协议时的关键技巧，往往就是给同一个值设计多条计算路径，而每条路径只用局部信息。

第 (3) 步：解密支付指令。

DB(EB(PI))=PID_{B}\big(E_{B}(\mathrm{PI})\big)=\mathrm{PI}DB​(EB​(PI))=PI

翻译成人话：银行用自己的私钥解开密文，终于看到卡号、有效期、金额——可以查余额、扣款、授权了。这一步只有银行能做，商家就算把 EB(PI)E_{B}(\mathrm{PI})EB​(PI) 抄下来也解不开，这正是第 (4) 条需求「安全」的实现。

补为什么第 (2) 步验签要放在第 (3) 步解密之前？ 两个理由：①先验后解是密码协议的基本卫生习惯——如果密文是攻击者伪造的（比如构造畸形数据），先解密可能触发实现上的漏洞，而先验签能直接把它挡在门外；②省算力——验签失败就不必再做一次 RSA 解密。真实系统里这条原则叫「先认证、后处理」。

第 (4) 步：返回支付授权。

{EM(DB(GP))} ⟶ M\Big\{E_{M}\big(D_{B}(\mathrm{GP})\big)\Big\}\ \longrightarrow\ M{EM​(DB​(GP))} ⟶ M

翻译成人话：银行用自己的私钥对某个值 GP\mathrm{GP}GP 签名（表示「这笔支付我担保」），再用商家的公钥把签名加密，发回给商家。里面一层 DB(⋅)D_{B}(\cdot)DB​(⋅) 是银行的承诺（签名本身是公开可验的：谁拿到它，谁就能用 EBE_{B}EB​ 验），外面一层 EM(⋅)E_{M}(\cdot)EM​(⋅) 是信封（只有商家能拆）。课件原文是「返回一个使用 EME_{M}EM​ 加密的数字签名 {EM(DB(GP))}\{E_{M}(D_{B}(\mathrm{GP}))\}{EM​(DB​(GP))} 授权给商家，来担保支付」。

补GP\mathrm{GP}GP 在课件中没有定义。 按上下文（「授权给商家，来担保支付」）应当理解为银行签发的支付授权凭证，内容至少包括这笔交易被批准的金额与交易标识。课件没给字段，是为了把注意力留在「银行签名」这件事上。你只要记住：GP\mathrm{GP}GP 是什么不重要，「DB(GP)D_{B}(\mathrm{GP})DB​(GP) 是银行不可抵赖的付款承诺」才重要。（真实 SET 里，这一步对应的凭证是支付网关返回的授权凭证，英文常称 payment token，含义相同。）

补既然签名本来就能被所有人验证，为什么外面还要再加密一层？ 因为签名只保证「内容是真的」，不保证「内容不给别人看」。授权凭证里通常含有金额、账户、交易号等敏感信息，如果明文广播，等于把交易细节公开了。「签名 + 加密」= 可验证 + 只给指定的人看，这个组合在协议里反复出现，值得单独记住。

用上一节的玩具数字把银行的验签走一遍（保持连续性，7a1 是 GSOMD\mathrm{GSOMD}GSOMD、c4e 是 PIMD\mathrm{PIMD}PIMD、9f2 是 POMD\mathrm{POMD}POMD）：

  银行手上：GSOMD="7a1"（商家转来）、DS、E_B(PI)
  银行自己算：H(E_B(PI)) = "c4e"

  右边：E_C(DS) = E_C(D_C("9f2")) = "9f2"
  左边：H("c4e" || "7a1") = H("c4e7a1") = "9f2"

  左边 == 右边  →  银行认证了持卡人的签名
  接着：D_B(E_B(PI)) → PI（卡号、金额，可扣款）
  最后：{ E_M(D_B(GP)) } → 商家（授权已发出）

算法 4：商家的收条（PPT 第 13 页）

课件第 13 页在银行步骤之后紧接着写：

商家应该做如下步骤：(1) 返回一个使用 ECE_{C}EC​ 加密的数字签名 {EC(DM(TC))}\{E_{C}(D_{M}(\mathrm{TC}))\}{EC​(DM​(TC))} 收条给持卡人，表明交易已经完成。

翻译成人话：商家用自己的私钥对「交易收条」TC\mathrm{TC}TC 签名，再用持卡人的公钥加密，发给持卡人。持卡人用自己的私钥拆开信封，再用商家的公钥验签，就得到一张商家亲笔承诺「这笔交易已经完成」的电子收据。

补TC\mathrm{TC}TC 在课件中同样没有定义，按字面应理解为 transaction confirmation（交易确认/收条），内容通常包括定单号、金额、时间、商家标识。它和 GP\mathrm{GP}GP 的关系是：GP\mathrm{GP}GP 是银行说「钱可以付」，TC\mathrm{TC}TC 是商家说「货我认了、交易成立」——两张凭证，两个承诺人。

补课件在算法 4 里只写了「返回收条」一步，但商家在此之前必然还有一个动作：取回并验证银行的授权。 这个动作不是课件的遗漏，而是上一页图里第 3 条消息的必然配套——商家收到 {EM(DB(GP))}\{E_{M}(D_{B}(\mathrm{GP}))\}{EM​(DB​(GP))} 之后，要做两件事：①用自己的私钥解开外层，得到 DB(GP)D_{B}(\mathrm{GP})DB​(GP)；②用银行的公钥验证 EB(DB(GP))=GPE_{B}(D_{B}(\mathrm{GP}))=\mathrm{GP}EB​(DB​(GP))=GP，确认这真是银行签发的授权，而不是别人伪造的。只有验过银行签名，商家才敢发货。 这两步加上收条，构成完整的「收尾」。

于是整条协议一共四层包装，每一层都遵循同一个模式：签名用私钥、加密用对方公钥。

消息 发送方 → 接收方 内容 内层（承诺） 外层（信封） 谁能拆
① C → M 定单 + 双重签名 + 支付摘要 + 支付密文 DS=DC(POMD)\mathrm{DS}=D_{C}(\mathrm{POMD})DS=DC​(POMD) EM(GSO)E_{M}(\mathrm{GSO})EM​(GSO) M
② M → B 定单摘要 + 双重签名 + 支付密文 （转发 DS\mathrm{DS}DS） EB(PI)E_{B}(\mathrm{PI})EB​(PI) B
③ B → M 支付授权 DB(GP)D_{B}(\mathrm{GP})DB​(GP) EM(⋅)E_{M}(\cdot)EM​(⋅) M
④ M → C 交易收条 DM(TC)D_{M}(\mathrm{TC})DM​(TC) EC(⋅)E_{C}(\cdot)EC​(⋅) C

补这张表建议背下来。 它把「谁签、给谁、谁能看」三件事压缩成一张四行的表，考场上问到「某一步为什么要用某个密钥」时，只要查表：内层永远是签名者的私钥，外层永远是收件人的公钥。

完整协议流程（PPT 第 14 页）

课件第 14 页用一张三角图把四条消息串起来。把它画成 ASCII：

   ①  C ─────▶ M    {E_M(GSO), DS, PIMD, E_B(PI)}
   ②  M ─────▶ B    {GSOMD, DS, E_B(PI)}
   ③  B ─────▶ M    {E_M(D_B(GP))}
   ④  M ─────▶ C    {E_C(D_M(TC))}

   拓扑：C ──①──▶ M ──②──▶ B ；B ──③──▶ M ──④──▶ C
        （C 与 B 之间没有直接信道，所有消息都经过商家 M 中转）

请注意这张图的拓扑：持卡人和银行之间没有直接连线，所有消息都经过商家。这一点很容易被忽略，但它有实际后果：

  • 持卡人从头到尾不需要直接联系银行（想想要在浏览器里给每家银行装插件有多麻烦）；
  • 银行从不直接接触持卡人，它对持卡人的信任完全来自「双重签名验过了」；
  • 商家是中转站，但中转站看得到的只是「密文 + 摘要 + 签名」——它可以转发，却看不懂不属于自己的部分。

补真实 SET 的流程比这张三角图复杂：还有证书交换与验证、持卡人证书与商家证书的互相认证、交易号（防止重放）、支付网关与收单行的分离等。课件这张图是「双重签名视角下的最小流程」，省略的部分在第 15 页第 (4) 条评述里被一句话带过——「在实际执行中，还需要一些步骤来确保各方认证特性」。考试与理解都抓住这四条消息即可，但要知道省略了什么。

评述：既连接又分离（PPT 第 15 页）

课件第 15 页给了四点评述，是这一章最值得逐字读的一页：

（1）「商家仅仅能看到支付指令的加密形式 EB(PI)E_{B}(\mathrm{PI})EB​(PI)，因此，不能看到信用卡信息。」

商家手里确实有 EB(PI)E_{B}(\mathrm{PI})EB​(PI) 这一整段密文，但它是用银行公钥加密的，商家没有 DBD_{B}DB​，所以解不开。它对着这段密文能做的只有转发；它手里那个 PIMD\mathrm{PIMD}PIMD 是从持卡人那里直接收到的，不是从密文里算出来的。而摘要不可逆，也推不出卡号。这一条保证了「需求 (4) 安全」在商家这一侧成立。

（2）「商家和银行都不可能修改任何信息，这一点由签名 DSDSDS 保证。」

补这句话的准确含义是「改了一定会被发现」，不是「物理上改不了」。 商家当然可以在自己的电脑上把定单里的「1 台」改成「10 台」，但改完之后 GSOMD\mathrm{GSOMD}GSOMD 变了，验签等式两边不再相等，银行会拒绝授权、持卡人也能拿 DS\mathrm{DS}DS 证明原文是什么。 密码学提供的是可检测性（tamper-evident），不是不可修改性（tamper-proof）。这一点在现实安全里非常关键：检测得到篡改，就等于篡改没有收益。

具体到每一种篡改，谁会发现、怎么发现：

篡改者与动作 后果 谁会发现
商家改 GSO（数量、价格、地址） GSOMD\mathrm{GSOMD}GSOMD 变 → 银行验签失败 银行（拒绝授权）；持卡人（可出示 DS\mathrm{DS}DS 对照）
商家改 PIMD\mathrm{PIMD}PIMD 或伪造支付摘要 POMD\mathrm{POMD}POMD 与 DS\mathrm{DS}DS 不符 银行验签失败
商家改转发的 GSOMD\mathrm{GSOMD}GSOMD 银行算出的 POMD\mathrm{POMD}POMD 与 DS\mathrm{DS}DS 不符 银行验签失败
银行伪造或篡改支付授权 GP\mathrm{GP}GP EB(DB(GP))E_{B}(D_{B}(\mathrm{GP}))EB​(DB​(GP)) 对不上 商家用 EBE_{B}EB​ 验签失败，可以拒绝发货
任何人改 DS\mathrm{DS}DS 本身 还原出的 POMD\mathrm{POMD}POMD 不对 所有验证者
攻击者重放整条旧交易 单看密码学无法区分新旧 需要交易号/时间戳（第 (4) 条要补的）

（3）「银行仅仅能看到 hash 值 GSOMD\mathrm{GSOMD}GSOMD，因此，不能确定定单内容。」

银行能验证「这个 POMD\mathrm{POMD}POMD 里确实锁着一份定单」，却不知道定单里写的是什么——它只看到一个几十字节的摘要。这一条保证了「需求 (3) 隐私」在银行这一侧成立。 注意这里的不对称：银行需要知道金额（在 PI 里，它能解开），但不需要知道商品明细（在 GSO 里，它只有摘要）。「能验证」和「能读懂」被拆开了——这是双重签名最精妙的一点。

（4）「在实际执行中，还需要一些步骤来确保各方认证特性。」

这句话是本节的「边界声明」。它承认：双重签名只解决了「数据绑定 + 互相保密」，没有解决「你怎么知道对面是谁」。 具体缺什么：

缺的能力 缺了会怎样 真实 SET 怎么补
身份与公钥的绑定 攻击者可发假公钥，冒充商家或银行 X.509 证书 + CA
交易的新鲜性 攻击者可重放旧交易 交易号、时间戳、随机数
持卡人资质 银行不知道这张卡有没有钱、是不是黑卡 发卡行在线授权
商家的合法性 持卡人不知道这家店是不是真存在 商家证书、收单行背书
收条的可追溯 纠纷时说不清哪笔是哪笔 定单号、日志、对账

补所以「双重签名」在整套 SET 里的位置是：认证体系之上的一层「数据流控制」。 证书回答「你是谁」，双重签名回答「这两份数据是不是同一笔交易、该给谁看」。两者缺一不可，而本讲只讲后者。理解这个分层，你就不会误以为「有了双重签名就安全了」。

最后用一句话收住整套协议的设计思想：

一个签名锁两份文件，但把两把钥匙孔分给两个人。

商家有「定单全文 + 支付摘要」这把钥匙孔，银行有「支付全文 + 定单摘要」这把钥匙孔，两边都能验证同一个 DS\mathrm{DS}DS，两边都看不到对方那份全文。持卡人只需要签一次名。连接靠摘要，分离靠加密，认证靠签名——这三句话就是双重签名的全部。

本节要点

  • 算法 3（银行）：算 PIMD=H(EB(PI))\mathrm{PIMD}=H(E_{B}(\mathrm{PI}))PIMD=H(EB​(PI)) → 用 EC(DS)=H(H(EB(PI))∥GSOMD)E_{C}(\mathrm{DS})=H(H(E_{B}(\mathrm{PI}))\|\mathrm{GSOMD})EC​(DS)=H(H(EB​(PI))∥GSOMD) 验签 → 解出 PI\mathrm{PI}PI → 返回 {EM(DB(GP))}\{E_{M}(D_{B}(\mathrm{GP}))\}{EM​(DB​(GP))} 授权。
  • 算法 4（商家）：取回并验证银行授权 → 返回 {EC(DM(TC))}\{E_{C}(D_{M}(\mathrm{TC}))\}{EC​(DM​(TC))} 收条，交易完成。
  • 四条消息的拓扑是「C–M–B 三角，C 与 B 不直接相连」，商家只是中转站。
  • 第 15 页四点评述：商家看不到卡号（需求 4）、篡改必被发现（需求 2）、银行不知道定单内容（需求 3）、还需补齐认证特性（证书、交易号等）。
  • 密码学保证的是可检测的篡改（tamper-evident），不是物理不可改；「能验证」与「能读懂」是两件事。
  • 双重签名只解决数据绑定与保密，不解决身份认证与新鲜性——那是 PKI 和交易号要补的课。
