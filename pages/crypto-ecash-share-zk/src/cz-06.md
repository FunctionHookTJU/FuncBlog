第 5 页把镜头拉到了具体场景：一个人在网页上按下「提交定单」。这一按之后，至少有两份数据要离开他的电脑——一份描述「买什么」，一份描述「怎么付钱」。第 6 页用四条规定告诉你这两份数据各要满足什么，第 7 页介绍专门为此设计的 SET 协议，第 8 页把协议的参与方和数据元素点清楚。本节按这四页的顺序走，并且在最后把「四条需求为什么会互相打架」讲明白——**正是这个打架，逼出了下一节的双重签名。**

### 1.1 需求分析：先问「要保护什么」（PPT 第 5 页）

课件第 5 页给了这一章的总前提：

> 每当用户需要在 internet 上进行电子交易下达定单时，这些数据都必须得到适当保护，以避免信用欺诈并保护用户的个人隐私。

这句话里有两个关键词：**避免信用欺诈**（fraud，对应钱的安全）和**保护个人隐私**（privacy，对应信息的安全）。请注意它们是**两个不同的目标**，不是一个目标的两个说法：

- 信用欺诈的受害者是**银行和持卡人**，损失是**钱**，典型形式是别人用你的卡号刷走一笔。
- 隐私泄露的受害者是**持卡人**，损失是**信息**，典型形式是别人知道你什么时候买了什么、寄到哪里。

【补】**为什么要把这两件事分开？** 因为它们的防护手段完全不同。防欺诈要靠「确认是你本人、确认金额、确认没被改」，是**认证与完整性**问题；防隐私泄露要靠「让不该看的人看不到内容」，是**机密性**问题。更麻烦的是，这两条要求在某些设计里是**互相冲突**的——这个冲突就是本节后半段和下一节的主题。

### 1.1.1 四条需求逐条读（PPT 第 6 页）

课件第 6 页把需求列成四条，文字非常短，短到很容易被当成口号背过去。先把原文整理成表（这张表建议直接背）：

| 编号 | 需求 | 课件原文 | 要防的攻击 | 若失守的后果 |
|---|---|---|---|---|
| (1) | **认证**（authentication） | 交易中的参与者都是真实的，不存在冒充者，并且签名不存在伪造的情况 | 冒充者、伪造签名 | 假商家骗卡号、假客户骗货、假银行骗授权 |
| (2) | **真实**（integrity） | 各种文件如定单和帐单不能被变更 | 篡改 | 改数量、改价格、改收货地址、改金额 |
| (3) | **隐私**（privacy） | 具体的交易细节应该尽量保证安全 | 交易细节被旁观者看到 | 别人知道你买了什么、买了多少 |
| (4) | **安全**（security） | 敏感的帐户信息如信用卡号应该得到保护 | 账户信息被窃取 | 卡号泄露，被盗刷 |

这张表有四列值得多说一句：**「要防的攻击」这一列是课件没写的，但它是判断一条需求有没有被满足的唯一可操作标准。** 需求写得再漂亮，如果说不清「它在防谁做什么」，就无法验收。下面逐条展开。

#### (1) 认证：交易中的参与者都是真实的

课件原话把「认证」拆成两半：**「不存在冒充者」**和**「签名不存在伪造的情况」**。这两半听起来像同一件事，其实分别对应两个不同的攻击：

- **冒充（impersonation）**：攻击者假装成某一方，比如做一个和真商家一模一样的假网站，让你把卡号输进去。这里的破绽不在密码学，而在「你怎么知道对面真的是他」——需要**证书**（certificate）把公钥和一个身份绑起来。
- **伪造签名（forgery）**：攻击者不冒充身份，而是伪造一份「你签过」的文件。这里的破绽在密码学本身——需要签名方案是安全的，别人没有你的私钥就造不出能通过验证的签名。

【补】**为什么这两半必须分开讲？** 因为「认证」这个词在工程上被用了两次。第一次是**身份认证**（Authentication，证明「你是你」），第二次是**消息认证**（Message Authentication，证明「这条消息来自你且没被改」）。课件这句话前半句说身份，后半句说消息，合起来才是完整的第一条需求。

#### (2) 真实：各种文件不能被变更

这一条的关键词是**「各种文件」**和**「不能被变更」**。它管的不是「谁说的」，而是「说的内容有没有被改」。攻击者的动作很具体：

- 把定单里的「1 台」改成「10 台」，付 1 台的钱拿 10 台；
- 把价格从 3999 元改成 39.99 元；
- 把收货地址改成攻击者自己的地址；
- 把支付指令里的金额改小，或者把收款账号改掉。

【补】**「真实」这个词在这里其实翻译得不够准。** 英文原文很可能是 integrity（完整性），课件译作「真实」。严格说，「真实」强调的是「这份文件确实出自其声称的作者」，而「完整性」强调的是「内容没有被改动」。这两件事在数字签名里是同一个机制同时保证的，所以课件把它们合在一条里讲，问题不大；但你要知道**这一条的技术核心是完整性，不是真实性**。

对策是「摘要 + 签名」：先把整份文件压成一个摘要，再对摘要签名。文件改一个字符，摘要就完全不同，验证立刻失败。这也是后面双重签名所有公式的基本套路。

#### (3) 隐私：具体的交易细节应尽量保证安全

这一条最容易和第四条混淆。课件用词很讲究：**「具体的交易细节」**——买的是什么、买了几个、寄给谁、什么时候买的。这些信息泄露出去，损失不是钱，而是**「别人知道了不该知道的事」**。

【补】**为什么交易细节值得保护？** 因为交易记录能拼出一幅相当完整的生活画像：买了什么药能推出健康状况，买了婴儿用品能推出家庭情况，买了书能推出政治倾向，收货地址能推出住址，下单时间能推出作息。这些信息单独看没什么，**串起来就是一份档案**。课件用「尽量保证安全」这种留有余地的说法，是因为隐私保护在真实系统里总要在可用性和保密性之间折中（比如商家必须知道收货地址才能发货，所以地址不可能对商家保密）。

#### (4) 安全：敏感的账户信息如信用卡号应得到保护

这一条的用词也很讲究：**「敏感的帐户信息」**——卡号、有效期、持卡人姓名、校验码。这些信息的泄露后果是**直接的钱**：卡号加有效期足以在很多场景完成无卡支付。

【补】**注意第 (3) 条和第 (4) 条的分工，这是全讲最重要的一次切分：**

| | 第 (3) 条「隐私」 | 第 (4) 条「安全」 |
|---|---|---|
| 保护对象 | 交易细节（GSO 那一类内容） | 账户信息（PI 那一类内容） |
| 典型内容 | 买了什么、数量、价格、收货地址 | 卡号、有效期、持卡人姓名 |
| 谁**必须**知道 | 商家（否则没法发货） | 银行（否则没法扣款） |
| 谁**绝不能**知道 | 银行（它不需要知道） | 商家（它不需要知道） |
| 泄露后果 | 隐私被侵犯 | 钱可能被盗刷 |

这张表你如果只能记一行，就记最后两行：**商家必须看定单、银行必须看卡号；反过来，银行不该看定单、商家不该看卡号。** 这句话就是下一节「问题所在」的全部内容，也是双重签名存在的理由。

下面这张图把「谁必须看到什么」画出来，后面所有协议设计都是为了让这张图成立：

```
   商家 M 必须看全：GSO                银行 B 必须看全：PI
   · 持卡人姓名                        · 商家名字
   · 商家姓名                          · 信用卡号
   · 商品与数量                        · 全部商品价格
   · 价格
        │                                   │
        ▼                                   ▼
   只知道「买了什么」                 只知道「怎么付钱」
        └──────── 交叠字段：商家名字、价格 ────────┘
```

### 1.1.2 四条需求不是并列的，它们会互相打架

课件把这四条并列排出来，容易让人以为「把四个都做到就完了」。但真正做协议时会发现，**第 (2) 条和第 (3)(4) 条的要求方向是相反的**：

- 第 (2) 条要求「定单和支付指令都不能被改」，最直接的做法是**让同一方对两份文件都签名，并且把两份文件都发给同一个人验证**——这样谁都能检查它们对得上。
- 第 (3)(4) 条要求「银行看不到定单、商家看不到卡号」，最直接的做法是**把两份文件分别只发给对应的人**——但这样就没有人能同时看到两份文件了。

于是冲突出现了：**要保证「两份文件对得上」，就得让某个人同时看到两份；要保证「各看各的」，就不能让任何人同时看到两份。** 这两条在明文世界里无法同时满足。

【补】**这个冲突在数学上的准确表述**：如果持卡人对 GSO 和 PI 分别签两个独立的签名，那么

$$\mathrm{Sig}_{C}(\mathrm{GSO}),\qquad \mathrm{Sig}_{C}(\mathrm{PI})$$

**翻译成人话**：这是两份各自有效的签名，一份说「我下这个定单」，一份说「我付这笔钱」。看起来没问题，但**两个签名之间没有任何数学联系**——任何人都可以拿这第一份签名配上别的支付指令，或者拿这份支付指令配上别的定单，因为验证者检查的是两个独立的等式，它们各自都成立。**签名只证明了「每份文件都被 C 签过」，没有证明「这两份是同一笔交易」。**

这正是下一节 1.2.2 要讲的问题。这里先埋一个伏笔：解决办法不是「让某一方多看一点」，而是**设计一种一次签名同时覆盖两份文件、但验证时只需要自己那份全文的签名**——这就是双重签名。

### 1.2 SET 协议：在现有信用卡体系上加一层（PPT 第 7 页）

课件第 7 页交代 SET 的来历：

> 1996 年，信用卡公司 MasterCard 和 Visa 征集建立电子商务标准。成果就是它们联合几家公司提出了 SET 协议。SET 是设计在现有信用卡系统之上并保障人们可在公共信道上安全使用系统的技术。SET 协议十分复杂，涉及许多技术细节。下面，我们将讨论协议的一个方面，也就是，双向签名的使用。

这段话有四个信息点，每个都值得展开：

**① 时间与发起者：1996 年，MasterCard 与 Visa。** 这两家是当时全球最大的两个信用卡组织，它们**联合**发布标准，说明这件事不是某家公司的产品功能，而是**整个支付行业的互操作规范**。两家竞争公司愿意坐下来定标准，本身就说明「网上支付不安全」已经成了行业级问题。

**② 「联合几家公司」**：信用卡支付不是两家卡组织能单独完成的，中间还有发卡行、收单行、支付网关、软件厂商。SET 的规范里对每一方要装什么证书、走什么消息都有规定，所以它「十分复杂」。

**③ 「设计在现有信用卡系统之上」**：这半句非常关键。SET 不发明新的货币，也不取代信用卡网络，它只是在**原有的授权/清算流程外面加一层密码学包装**。持卡人还是那些人、卡还是那些卡、银行还是那些银行，变的只是「消息怎么写、怎么验」。这也是为什么 SET 能落地（至少在规范层面），而「电子现金」那种要另建一套货币体系的东西只能慢慢来。

**④ 「保障人们可在公共信道上安全使用系统」**：这里再次出现「公共信道」。SET 的前提假设就是**信道不可信**——所有安全性都由消息本身提供，而不指望网络是安全的。这个假设叫「**敌手控制信道**」（adversary-controlled channel），是现代密码协议的标准假设。

【补】**SET 的完整名字与技术底座**：SET = Secure Electronic Transaction（安全电子交易）。它 1997 年发布 1.0 版，技术上依赖 **X.509 数字证书**（给持卡人、商家、支付网关各发一张证书）和 **RSA**（签名与加密）。它在 2000 年代并没有大规模普及，主要原因是**太复杂、太贵**：每个参与者都要申请证书、要做专门的软件，而当时的浏览器和服务器性能有限。但它的**双重签名**设计非常漂亮，成了所有密码学教材讲「一个签名绑定两份数据」的标准例子，这也是本讲仍然讲它的原因。

【补】**「在现有体系之上」意味着哪些东西必须保留？** 至少要保留三样：①**发卡行**（你的卡是哪家银行发的，钱从它账上扣）；②**收单行**（商家在哪家银行开户，钱进它账上）；③**卡组织清算网络**（跨行之间怎么结算）。这三样是法律和金融基础设施，密码学改不了它们。所以 SET 的协议里，「银行」这个角色实际上是**一组银行**的抽象，本讲的模型把它简化成单个 B。

课件最后一句是重要的边界声明：**SET 十分复杂，本讲只讨论它的一个方面——「双向签名」的使用。** 也就是说，本讲不打算讲完 SET，只讲其中那个最漂亮、也最能体现「给签名装附加功能」的部分。

| SET 完整规范要解决的问题 | 本讲是否涉及 |
|---|---|
| 证书申请、颁发、吊销（PKI） | 不涉及 |
| 持卡人注册、商家注册流程 | 不涉及 |
| 消息格式、字段编码、传输协议 | 不涉及 |
| **一笔交易里两份数据如何绑定、如何互相保密** | **本节到 1.2.3（第 8–15 页）** |
| 支付授权、清算、对账 | 只讲到「银行返回授权」为止 |

【补】**术语统一**：课件第 7 页和第 11 页把 dual signature 译成「**双向签名**」，有的中文教材译作「**双重签名**」。本讲义统一用「**双重签名**」，看到课件里的「双向签名」请当作同一个东西。

### 1.2.1 元素：三方与两条信息（PPT 第 8 页）

课件第 8 页把协议的「零件」列了出来：参与者和持卡人的两条信息。

#### 参与者：三方

- **银行（Bank，B）**：负责发卡、授权支付、清算。它掌握持卡人的账户信息和信用额度，是唯一有资格说「这笔钱可以付」的一方。
- **持卡人（Cardholder，C）**：买东西的人，持有信用卡和对应的私钥。
- **商家（Merchant，M）**：卖东西的人，负责发货、向银行请求授权。

【补】**真实 SET 里「银行」其实是两个角色**：**发卡行**（issuer，给持卡人发卡、承担信用风险）和**收单行**（acquirer，给商家开户、把钱打给商家）。本讲的模型把它们合并成一个 B，是因为双重签名的逻辑只关心「有一个掌握卡号、能授权付款的实体」，不关心它内部怎么分账。做题和写协议时按三方处理即可。

#### 持卡人的两条信息

课件第 8 页对两条信息的定义如下（这张表是本节的核心，务必记住字段构成）：

| 信息 | 全称 | 应该包括的字段 | 谁必须看全 | 谁绝不能看全 |
|---|---|---|---|---|
| **GSO** | 商品和服务定单（Goods and Services Order） | 持卡人和商家的名字、订购商品与数量、价格等 | **商家 M**（要发货、要开票） | 银行 B（只需知道有这笔交易） |
| **PI** | 支付指令（Payment Instruction） | 商家的名字、信用卡号、全部商品的价格等 | **银行 B**（要扣款、要授权） | 商家 M（只需知道钱到账） |

请特别注意两条信息**交叠**的部分：**商家的名字**和**价格**在两条信息里都出现。这不是冗余，而是设计的关键：

- **商家名字**在两边都有，是为了让银行确认「这笔钱付给的是谁」，也让商家确认「这笔定单是给我自己的」。
- **价格**在两边都有，是为了让银行确认「授权金额和定单金额一致」——否则商家可以拿一张 39.99 元的定单去请求 3999 元的授权。

【补】**为什么这样切分字段？** 切分的标准只有一个：**这份信息是「为了把货送到」还是「为了把钱划走」**。凡是为了发货的（商品、数量、收货地址、持卡人姓名）都进 GSO；凡是为了扣款的（卡号、账户信息）都进 PI；而两边都必须知道的公共字段（商家名、金额）就**同时出现在两份里**——这个「同时出现」在密码学上要付出代价：**两份信息必须被同一个签名锁在一起**，否则攻击者可以拿 A 的支付指令配 B 的定单，让金额对不上。这就是下一节要展开的「连接」问题。

用本节一直在用的例子把两条信息填实：学生小林在「星光数码」网店买了一台 3999 元的手机。

```
   GSO（给商家的定单）                  PI（给银行的支付指令）
   ─────────────────────────             ─────────────────────────
   持卡人：小林                          商家：星光数码
   商家：星光数码                        信用卡号：6222 **** **** 1234
   商品：手机 × 1                        全部商品价格：3999.00 元
   价格：3999.00 元
   收货地址：天津市 ……
              │                                        │
              ▼                                        ▼
        只有商家该看全                            只有银行该看全
        （银行最多知道「有一单」）              （商家最多知道「钱付了」）
```

### 本节要点与下一步

- 第 5 页定调：电子交易数据必须保护，目标是**避免信用欺诈**和**保护个人隐私**，这是两个不同的目标。
- 第 6 页四条需求：**认证**（防冒充与伪造签名）、**真实**（防篡改）、**隐私**（防交易细节泄露）、**安全**（防卡号等账户信息泄露）。
- 第 7 页 SET：1996 年 MasterCard 与 Visa 联合发起，**建立在现有信用卡体系之上**，只解决「公共信道上安全使用」；本讲只讲其中的双重签名。
- 第 8 页元素：三方（银行、持卡人、商家）+ 两条信息（GSO 给商家看全文、PI 给银行看全文），两条信息在商家名与价格上**交叠**。
- 下一节要解决的核心矛盾：**两条信息必须被连接起来（否则可以张冠李戴），但又必须对彼此保密（否则隐私和安全都没了）。**
