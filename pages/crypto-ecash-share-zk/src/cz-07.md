上一节我们把「四方需求」和「两条信息」摆好了，也看出了矛盾：定单要连着支付指令，可两边又不能互相看见。这一节解决它。课件第 9 页把矛盾说清楚，第 10 页交代工具和记号，第 11、12 页给出**双重签名**的构造与验证——也就是本讲第一个「给签名装附加功能」的成品。这一节公式比较密，请对照课件页图一并看。

### 1.2.2 问题所在：既要连接，又要分开（PPT 第 9 页）

课件第 9 页的话很短，但每一句都是设计约束：

> 银行不应该知道持卡人的定单情况，而出于安全考虑，商家不应该知道信用卡号。但是，这两条信息应该以一定的方式加以连接。否则，商家可能将支付信息与其他的定单相连接。

把它拆成三条硬约束：

| 约束 | 内容 | 谁受益 | 靠什么实现 |
|---|---|---|---|
| 约束一 | 银行**不应该知道**持卡人的定单情况 | 持卡人的隐私 | 银行只拿到定单的摘要，拿不到定单原文 |
| 约束二 | 商家**不应该知道**信用卡号 | 持卡人的钱 | 商家只拿到支付指令的密文 |
| 约束三 | 两条信息**必须连接**起来 | 持卡人 + 银行 | 同一个签名同时覆盖两份文件的摘要 |

前两条很容易理解——它们就是上一节第 (3)(4) 条需求的直接翻译。**难的是第三条，而且第三条和前两条在方向上正好相反。** 课件用「否则」两个字提示了后果，但没有展开攻击过程。下面把它展开：

**攻击一：移花接木（一份支付凭证配另一张定单）。** 假设没有任何连接机制。持卡人小林对「1 台手机、3999 元」的定单签了字，也对「3999 元」的支付指令签了字，两份签名各自有效。商家拿到这两份东西后，可以**把支付凭证留下来，却发一份便宜得多的货**（比如 399 元的旧款），事后声称「客户下单的就是这一款」。银行这边看到的是：支付指令签名有效、金额 3999 元——照付。由于支付指令上没有绑定「买的是什么」，小林**无法证明自己订的是手机**。这一条损害的是持卡人。

**攻击二：一笔付款抵两张单（重复挂接）。** 更狡猾的版本是：商家把小林这笔已经付款的支付凭证，拿去挂到**另一位客户的定单**上，对外宣称「这笔钱是那位客户付的」，从而让那位客户的订单也显示「已付款」而实际没收到钱。或者反过来，把一笔尚未授权的支付指令挂到一张金额相同的假定单上骗银行授权。这一条损害的是银行和其他客户。

这两个攻击的共同点是：**攻击者不需要伪造任何签名，他只需要「换一个搭配」。** 因为两份签名各管各的，换搭配之后每个签名仍然能验过。密码学里把这种「合法零件的非法组合」叫**重放/替换攻击**（replay / substitution attack）。

【补】**这个矛盾有个通用名字：绑定与保密的张力（binding vs. privacy）。** 想绑定，就得让某个人同时看到两份；想保密，就不能让任何人同时看到两份。**双重签名的漂亮之处在于：它找到了一种「谁都不需要看全」的绑定方式**——秘诀是把「看全文」换成「看摘要」，摘要不含内容，但能证明内容。

### 1.2.3 交易方案：先备好工具和记号（PPT 第 10 页）

课件第 10 页交代协议用到的密码学零件：

> 系统使用一个公开 hash 函数 $H$。公钥加密算法使用 RSA，并且持卡人、商家和银行拥有自己的公开和秘密密钥。令 $E_{C}$，$E_{M}$，和 $E_{B}$ 表示持卡人、商家、和银行的加密函数，而 $D_{C}$，$D_{M}$，和 $D_{B}$ 对应表示解密函数。

这一段是后面所有公式的「记号表」。逐项落实：

| 记号 | 含义 | 谁掌握 | 用来做什么 |
|---|---|---|---|
| $H$ | 公开的 Hash 函数 | 所有人都知道 | 把任意长的文件压成定长摘要 |
| $E_{C},E_{M},E_{B}$ | 分别用持卡人/商家/银行的**公钥**做运算 | 公开 | 加密（给谁看就用谁的） |
| $D_{C},D_{M},D_{B}$ | 分别用持卡人/商家/银行的**私钥**做运算 | 各自保密 | 解密，或者**签名** |

【补】**RSA 的一个方便之处：同一个运算两个方向都能用。** RSA 里加密和解密是互逆的同一套模幂运算，所以：

$$E_{X}\big(D_{X}(m)\big)=m,\qquad D_{X}\big(E_{X}(m)\big)=m$$

**翻译成人话**：用 X 的私钥作用一次、再用 X 的公钥作用一次，就还原了。于是「用私钥作用」可以当**签名**（只有 X 能做），「用公钥作用」可以当**验证**（谁都能做）。这就是为什么课件用同一对 $E$、$D$ 同时表示「加解密」和「签名验证」——**在 RSA 里这两件事是同一件事的两个方向。**

【补】**别被记号骗了**：不同教材里 $E$、$D$ 的用法不一样，有的把 $E$ 专指加密、签名另外用 $S$。本讲完全沿用课件记号：**$E_{X}$ = 用 X 的公钥作用，$D_{X}$ = 用 X 的私钥作用。** 看到 $D_{C}(\cdot)$ 就念成「持卡人签的」，看到 $E_{C}(\cdot)$ 就念成「用持卡人的公钥打开的」——验签就是后者。

【补】**Hash 函数 $H$ 在这里必须满足什么？** 至少三条：①**单向**——给定摘要算不出原文；②**抗碰撞**——找不到两份不同的文件有相同摘要；③**雪崩**——改一个比特，摘要面目全非。课件把它设为「公开」的，因为**每一方都要自己算摘要**：商家要算 $H(E_{M}(\mathrm{GSO}))$，银行要算 $H(E_{B}(\mathrm{PI}))$，如果有谁算不出来，协议就断了。

### 双重签名（dual signature）的核心思想：签「摘要的摘要」

在写公式之前，先把思想说清楚，否则四个步骤会像变戏法。

**目标：** 让持卡人 C 用一个签名 $DS$ 同时锁住两份文件，但要求验证者**只需要自己那份的全文 + 另一份的摘要**就能验证。

**办法：** 分三步走——

1. 两份文件各自算摘要：GSO 的摘要记作 $\mathrm{GSOMD}$，PI 的摘要记作 $\mathrm{PIMD}$；
2. 把两个摘要**按固定顺序拼接**，再算一次摘要，得到一个「总摘要」$\mathrm{POMD}$；
3. 对总摘要签名，得到 $\mathrm{DS}$。

画成图就是：

```
   E_M(GSO) ──H──▶ GSOMD ──┐
                           │
                           ├── 拼接 ──▶ PIMD || GSOMD ──H──▶ POMD ──D_C──▶ DS
                           │                                      │
   E_B(PI)  ──H──▶ PIMD ───┘                                      ▼
                                                          持卡人的双重签名
```

**为什么这样就「既连接又分开」？**

- **连接**：$\mathrm{POMD}$ 里同时含有 $\mathrm{PIMD}$ 和 $\mathrm{GSOMD}$ 的信息，而 $\mathrm{DS}$ 是对 $\mathrm{POMD}$ 的签名。改任何一份文件的任何一个字符，都会让对应的摘要变、让 $\mathrm{POMD}$ 变、让 $\mathrm{DS}$ 验不过。**两份文件被同一个签名锁死了。**
- **分开**：商家验证时只需要 $\mathrm{PIMD}$（一个短摘要）而不是 PI 全文；银行验证时只需要 $\mathrm{GSOMD}$ 而不是 GSO 全文。**没有人需要看到对方的完整文件。**

【补】**为什么不直接对「两份文件拼起来」签名？** 因为那样商家验签时必须拿到 PI 全文（否则拼不出一模一样的字节串），银行也必须拿到 GSO 全文——**保密性瞬间归零**。所以关键不是「拼接文件」，而是「拼接文件的摘要」：摘要短、不可逆、且足以代表原文。这个「摘要树」的结构在密码学里到处都是（证书链、区块链的 Merkle 树都是同一个思想）。

### 算法 1：持卡人 C 的四个步骤（PPT 第 11 页）

课件第 11 页先给了一句摘要，然后列四个步骤。摘要原文是：

> 摘要：持卡人通过 PI 向商家支付 GSO 的费用。

这句话确定了整笔交易的语义：**GSO 是「为什么付」，PI 是「怎么付」，两者必须指同一笔钱。** 下面是四个步骤。

**第 (1) 步：分别算两个摘要。**

$$\mathrm{GSOMD}=H\big(E_{M}(\mathrm{GSO})\big),\qquad \mathrm{PIMD}=H\big(E_{B}(\mathrm{PI})\big)$$

**翻译成人话**：先把定单用**商家的公钥**加密（这样只有商家能解开），再对这段密文求摘要，得到 $\mathrm{GSOMD}$；把支付指令用**银行的公钥**加密（这样只有银行能解开），再对密文求摘要，得到 $\mathrm{PIMD}$。两个摘要都是「给对方的信封」的指纹，**谁都能看这个指纹，但只有收件人能拆开信封**。

【补】**为什么摘要算在「密文」上，而不是算在原文上？** 三个理由：①摘要必须绑定「真正被传输的那串字节」，否则商家收到的密文和摘要对不上；②商家可以在**不解密的情况下**先核对 $\mathrm{GSOMD}$，避免对畸形的密文做解密运算；③密文里已经含有全部明文信息，摘要对着密文算与对着明文算在「防篡改」上效力相同，但多了一层「这段密文就是原件」的确认。记住一点就够了：**协议里所有摘要都对着「实际传输的那串字节」算。**

**第 (2) 步：拼接两个摘要，再算一次摘要。**

$$\mathrm{POMD}=H\big(\mathrm{PIMD}\,\|\,\mathrm{GSOMD}\big)$$

**翻译成人话**：把「支付摘要」和「定单摘要」按 **$\mathrm{PIMD}$ 在前、$\mathrm{GSOMD}$ 在后**的顺序连成一串，再求一次摘要，得到 $\mathrm{POMD}$。这个 $\mathrm{POMD}$ 就是「双重签名」真正签的那个东西——它同时代表了定单和支付指令。

【补】**顺序必须固定，而且这里是 $\mathrm{PIMD}$ 在前。** 这不是审美问题：如果允许两种顺序，同一对文件就能算出两个不同的 $\mathrm{POMD}$，签名的含义就有了歧义（攻击者可以把拼接顺序当成一个「自由度」来利用）。另外不必纠结 $\mathrm{POMD}$ 这三个字母怎么展开（课件没给定义），只要知道它是**两个摘要的摘要**就够了。

**第 (3) 步：对总摘要签名。**

$$\mathrm{DS}=D_{C}(\mathrm{POMD})$$

**翻译成人话**：持卡人用自己的**私钥**作用在 $\mathrm{POMD}$ 上，得到的就是双重签名 $\mathrm{DS}$。因为只有 C 有 $D_{C}$，所以这个 $\mathrm{DS}$ 只能由 C 产生——这就是「不可抵赖」的来源；而任何人用 $E_{C}$ 都能验证它——这就是「可公开验证」的来源。

**第 (4) 步：把四样东西发给商家。**

$$\{E_{M}(\mathrm{GSO}),\ \mathrm{DS},\ \mathrm{PIMD},\ E_{B}(\mathrm{PI})\}\ \longrightarrow\ M$$

**翻译成人话**：持卡人给商家寄四件东西——①给商家的**定单密文**（只有商家能解）；②双重签名；③**支付摘要**（注意：是摘要，不是支付指令！）；④给银行的**支付指令密文**（商家解不开）。**特别注意：没有 $\mathrm{GSOMD}$。** 因为商家自己就能从 $E_{M}(\mathrm{GSO})$ 算出 $\mathrm{GSOMD}$，没必要多传一个。

下面这个手算例子用「玩具摘要」把四步走一遍。真实系统里 $H$ 是 SHA-256 之类，输出 256 比特、也就是 64 个十六进制字符；这里为了看清算术，假设摘要只有 3 位十六进制，并且「改一个字就完全变样」的性质照样成立：

```
  假设：
    H(E_M(GSO)) = 7a1        ← GSOMD（定单密文的摘要）
    H(E_B(PI))  = c4e        ← PIMD （支付密文的摘要）

  第 (2) 步拼接（顺序：PIMD 在前）：
    PIMD || GSOMD = "c4e" + "7a1" = c4e7a1
    H("c4e7a1")   = 9f2      ← POMD

  第 (3) 步签名：
    DS = D_C("9f2")          ← 只有 C 能算出的签名值

  第 (4) 步发送：
    { E_M(GSO), DS, "c4e", E_B(PI) }  →  商家
```

商家收到的四样东西里，两样是密文、一样是签名、一样是摘要。**商家能从这堆东西里推出「这笔钱是为这张定单付的」，却推不出卡号——这正是设计目标。**

### 算法 2：商家 M 的验证与取回定单（PPT 第 12 页）

课件第 12 页列商家的四个步骤。

**第 (1) 步：自己算定单摘要。**

$$H\big(E_{M}(\mathrm{GSO})\big)=\mathrm{GSOMD}$$

**翻译成人话**：商家拿收到的定单密文，自己算一遍摘要，就得到了 $\mathrm{GSOMD}$。**这一步是在「补上商家缺的那块拼图」**——持卡人没把 $\mathrm{GSOMD}$ 发过来，商家自己算出来。

**第 (2) 步：验签。** 商家计算两个值并比较：

$$H\Big(\mathrm{PIMD}\,\big\|\,H\big(E_{M}(\mathrm{GSO})\big)\Big)\quad \overset{?}{=}\quad E_{C}(\mathrm{DS})$$

**翻译成人话**：右边是「用持卡人的公钥把签名还原成总摘要」——如果签名真是 C 做的，还原出来就是 $\mathrm{POMD}$；左边是「商家自己用收到的 $\mathrm{PIMD}$ 和自己算出的 $\mathrm{GSOMD}$，按同样顺序拼起来再求摘要」——这也是 $\mathrm{POMD}$。**两个 $\mathrm{POMD}$ 相等，就说明 C 确实对「这份定单 + 这份支付指令」签了字。** 课件原文的说法是「如果它们相等，则商家就认证了持卡人的签名」。

请把等式的两边看仔细：

- **左边**用的是 $\mathrm{PIMD}$（**摘要**，不是支付指令 $E_{B}(\mathrm{PI})$）——商家不需要、也不能解开支付指令；
- **右边**用的是 $E_{C}$（**公钥**）——商家不需要 C 的私钥，任何人都能验。

**第 (3) 步：解密定单。**

$$D_{M}\big(E_{M}(\mathrm{GSO})\big)=\mathrm{GSO}$$

**翻译成人话**：商家用自己的私钥解开定单密文，终于看到「小林、手机 1 台、3999 元、天津」这些内容，可以去备货发货了。**这一步只有商家能做**——正是「给谁看就用谁的锁」：定单是给商家看的，所以用商家的公钥锁。

**第 (4) 步：把验证材料转给银行。**

$$\{\mathrm{GSOMD},\ \mathrm{DS},\ E_{B}(\mathrm{PI})\}\ \longrightarrow\ B$$

**翻译成人话**：商家把「定单摘要 + 双重签名 + 支付指令密文」三样东西交给银行去要钱。注意这里**给的是 $\mathrm{GSOMD}$（摘要），不是 GSO 全文**——银行因此永远不知道小林买的是什么。而 $E_{B}(\mathrm{PI})$ 本来就是给银行的，商家从头到尾解不开。

用同一个玩具例子把验证走一遍：

```
  商家手上：E_M(GSO)、DS、PIMD="c4e"、E_B(PI)
  商家自己算：H(E_M(GSO)) = "7a1"

  右边：E_C(DS) = E_C(D_C("9f2")) = "9f2"
  左边：H("c4e" || "7a1") = H("c4e7a1") = "9f2"

  左边 == 右边  →  验签通过
```

**如果攻击者改了定单呢？** 假设链路上的攻击者把「手机 × 1」改成「手机 × 10」（或者商家自己偷偷改，企图以后拿另一张定单去对账）：

```
  改后：H(E_M(GSO')) = "b83"        （摘要完全变样）
  左边：H("c4e" || "b83") = H("c4eb83") = "d05"
  右边：E_C(DS) = "9f2"
  "d05" ≠ "9f2"  →  验签失败，商家不能确认签名
```

这就是第 (2) 条需求「真实」的实现方式：**摘要的雪崩效应 + 签名锁住摘要**。改一个字，整条链就断了。

### 两个验证者的对称美（为下一节铺垫）

到这里，商家这一侧的验证已经完成。请把商家的验证等式先记住：

$$E_{C}(\mathrm{DS})\;=\;H\Big(\mathrm{PIMD}\,\big\|\,H(E_{M}(\mathrm{GSO}))\Big)$$

下一节银行会用几乎一模一样的等式来验证，只是**把自己手上的东西换进去**：

$$E_{C}(\mathrm{DS})\;=\;H\Big(H(E_{B}(\mathrm{PI}))\,\big\|\,\mathrm{GSOMD}\Big)$$

**翻译成人话**：银行有支付指令的密文，所以能自己算出 $\mathrm{PIMD}=H(E_{B}(\mathrm{PI}))$；银行从商家那里收到 $\mathrm{GSOMD}$；两边拼起来求摘要，也应该等于用 $E_{C}$ 还原出的 $\mathrm{POMD}$。**同一份 $\mathrm{DS}$，被两个只知道一半信息的人分别验证成功**——这是双重签名最值得回味的地方：签名是「整体的」，验证却是「各自局部的」。

【补】**这里藏着双重签名的安全边界**：商家能做验证，是因为 C **主动把 $\mathrm{PIMD}$ 发给了他**；银行能做验证，是因为商家**主动把 $\mathrm{GSOMD}$ 转给了它**。也就是说，验证能力是**被分发**的，而不是天生的。这个观察在讨论「谁能向谁证明什么」时非常重要——第 15 页的评述和第 2 章不可否认签名都会回到这一点。

| 谁能看到什么（截至商家验签完成） | 持卡人 C | 商家 M | 银行 B |
|---|---|---|---|
| GSO 全文 | 有（自己写的） | **有**（解密得到） | 无 |
| PI 全文 | 有（自己写的） | **无**（只有密文与摘要） | 无（还没收到） |
| $\mathrm{GSOMD}$ | 有 | 有（自己算出） | 无 |
| $\mathrm{PIMD}$ | 有 | 有（C 发来） | 无 |
| $\mathrm{DS}$ | 有 | 有 | 无 |
| 卡号 | 有 | **无** | 无（还没收到） |

### 本节要点

- 第 9 页的矛盾：银行不该看定单、商家不该看卡号，但两条信息必须连接，否则商家可以「换搭配」——支付凭证配别的定单、一笔付款抵两张单。
- 第 10 页的工具：公开 Hash 函数 $H$、RSA、三方的公私钥；$E_{X}$ 用公钥、$D_{X}$ 用私钥（在 RSA 里签名与解密是同一个方向）。
- 双重签名的构造：**各自算摘要 → 拼摘要再算摘要 → 签总摘要**，即 $\mathrm{POMD}=H(\mathrm{PIMD}\|\mathrm{GSOMD})$、$\mathrm{DS}=D_{C}(\mathrm{POMD})$。
- 算法 1（C）：算 $\mathrm{GSOMD}$、$\mathrm{PIMD}$，拼出 $\mathrm{POMD}$，签名，把四样东西发给商家（**不含 $\mathrm{GSOMD}$**）。
- 算法 2（M）：自己算出 $\mathrm{GSOMD}$，用 $E_{C}(\mathrm{DS})=H(\mathrm{PIMD}\|H(E_{M}(\mathrm{GSO})))$ 验签，解密取定单，再把 $\{\mathrm{GSOMD},\mathrm{DS},E_{B}(\mathrm{PI})\}$ 转给银行。
- 这一节的本质：**用「摘要的摘要」把两份文件锁在同一个签名上，而让每个验证者只需要自己那一半的全文。**
