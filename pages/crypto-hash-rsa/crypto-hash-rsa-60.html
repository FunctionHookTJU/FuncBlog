3.11 RSA-OAEP（PPT 第 46–48 页）

补这是这一讲唯一一个"正向的解决方案"，也是现代 RSA 实现的标准做法。一定要读透。

OAEP 的构造（PPT 第 46 页）

PPT 原文：

令 fff 为一个 kkk 比特输入 kkk 比特输出的单向陷门函数 RSA。令 k0k_0k0​ 和 k1k_1k1​ 为 2k02^{k_0}2k0​ 和 2k12^{k_1}2k1​ 都是不可执行的操作步的参数（例如，k0=k1=128k_0 = k_1 = 128k0​=k1​=128）。明文消息 mmm 的长度为 n=k−k0−k1n = k - k_0 - k_1n=k−k0​−k1​（例如，k=1024k = 1024k=1024，n=768n = 768n=768）。令

G:{0,1}k0→{0,1}n+k1和H:{0,1}n+k1→{0,1}k0G: \{0,1\}^{k_0} \to \{0,1\}^{n+k_1} \quad \text{和} \quad H: \{0,1\}^{n+k_1} \to \{0,1\}^{k_0}G:{0,1}k0​→{0,1}n+k1​和H:{0,1}n+k1​→{0,1}k0​
都是随机函数。加密函数就是，
E(m)=f({m∥0k1⊕G(r)}∥{r⊕H(m∥0k1⊕G(r))})，E(m) = f\big(\{m \| 0^{k_1} \oplus G(r)\} \| \{r \oplus H(m \| 0^{k_1} \oplus G(r))\}\big)，E(m)=f({m∥0k1​⊕G(r)}∥{r⊕H(m∥0k1​⊕G(r))})，
这里 ∥\|∥ 是联接符，m∥0k1m \| 0^{k_1}m∥0k1​ 表示 mmm 与 k1k_1k1​ 比特个全 0 字符串的联接，rrr 是一个 k0k_0k0​ 比特的随机二进制串。

补先记住三个长度参数，这张表是读懂 OAEP 的前提：

符号 含义 典型值
kkk RSA 模 nnn 的比特长度（= 分组长度） 1024
k0k_0k0​ 随机串 rrr 的长度 128
k1k_1k1​ "补零"的长度 128
nnn 明文的长度 =k−k0−k1= k - k_0 - k_1=k−k0​−k1​ 1024−128−128=7681024-128-128 = 7681024−128−128=768

补注意"nnn"这个字母在这里被复用了——PPT 用 nnn 表示明文长度，而第 1 节里 nnn 一直表示 RSA 的模。读的时候要注意区分上下文（这也是 PPT 在排版上的一处小瑕疵，读的时候心里有数就行）。

补"2k02^{k_0}2k0​ 和 2k12^{k_1}2k1​ 都是不可执行的操作步"是什么意思？

意思是：2k02^{k_0}2k0​ 和 2k12^{k_1}2k1​ 大到没法穷举。因为这两个参数决定了"攻击者要猜的东西有多少种可能"：

  • k0=128k_0 = 128k0​=128 → 随机串有 21282^{128}2128 种 → 不可穷举 ✓
  • k1=128k_1 = 128k1​=128 → 同样不可穷举 ✓

所以这句话是在说"这两个参数取得足够大，攻击者猜不出来"。

补那两个函数 GGG 和 HHH 是什么？

G:{0,1}k0→{0,1}n+k1G: \{0,1\}^{k_0} \to \{0,1\}^{n+k_1}G:{0,1}k0​→{0,1}n+k1​
H:{0,1}n+k1→{0,1}k0H: \{0,1\}^{n+k_1} \to \{0,1\}^{k_0}H:{0,1}n+k1​→{0,1}k0​

两个方向相反的函数：

  • GGG 把 128 比特的 rrr → 896 比特（n+k1=768+128=896n + k_1 = 768+128 = 896n+k1​=768+128=896）
  • HHH 把 896 比特的输入 → 128 比特

PPT 说它们是"随机函数"——这是一种理想化的假设（数学证明里要求的）。实践中用密码 Hash 函数来代替：

G=Hash 函数,H=Hash 函数G = \text{Hash 函数}, \qquad H = \text{Hash 函数}G=Hash 函数,H=Hash 函数

PPT 第 48 页会明确说这一点（见下文）。

补现在看那个加密公式，把它拆成 4 步（PPT 第 47 页的图就是这个流程）：

E(m)=f( {m∥0k1⊕G(r)}⏟左半部分 ∥ {r⊕H(m∥0k1⊕G(r))}⏟右半部分 )E(m) = f\big(\ \underbrace{\{m \| 0^{k_1} \oplus G(r)\}}_{\text{左半部分}} \ \|\ \underbrace{\{r \oplus H(m \| 0^{k_1} \oplus G(r))\}}_{\text{右半部分}}\ \big)E(m)=f( 左半部分{m∥0k1​⊕G(r)}​​ ∥ 右半部分{r⊕H(m∥0k1​⊕G(r))}​​ )

把它画成结构图（对照 PPT 第 47 页的原图）：

   m (768比特)         0^{k₁} (128比特)         r (128比特，随机)
        │                     │                        │
        └────────┬────────────┘                        │
                 ↓                                     ↓
          ┌──────────────┐                        ┌─────────┐
          │ m ‖ 0^{k₁}   │  ← 896 比特            │    G    │ ← 128→896

                 │                                     │
                 │        ┌────────────────────────────┘

              │     (⊕)       │  ← 左半 = (m‖0^{k₁}) ⊕ G(r)

                      │
        ┌─────────────┴──────────────────┐
        │                                │
        ↓                                ↓
   ┌─────────┐                     ┌───────────┐

补这个结构叫"Feistel 型的两轮掩码"，理解它只需要抓住三件事：

第一件：左半 = 消息被 G(r)G(r)G(r) 掩码

左半=(m∥0k1)⊕G(r)\text{左半} = \left(m \| 0^{k_1}\right) \oplus G(r)左半=(m∥0k1​)⊕G(r)

因为 rrr 是随机的，G(r)G(r)G(r) 也是"随机的"（在理想假设下），所以左半部分看起来是随机比特串。

第二件：右半 = rrr 被 H(左半)H(\text{左半})H(左半) 掩码

右半=r⊕H(左半)\text{右半} = r \oplus H(\text{左半})右半=r⊕H(左半)

这是"双重掩码"——rrr 先被用于掩码消息，然后它自己也被别的值掩码了。所以攻击者从右半拿不到 rrr。

第三件：最后把左右两半拼起来（共 kkk 比特）送进 fff

E(m)=f(左半∥右半)E(m) = f(\text{左半} \| \text{右半})E(m)=f(左半∥右半)

补为什么"双重掩码"是必须的？ 这是 OAEP 设计里最精巧的地方。

假设只做单重掩码（左半 = m∥0⊕G(r)m \| 0 \oplus G(r)m∥0⊕G(r)，右半直接就是 rrr）：

攻击者看到右半就是 r
        ↓
于是他能算出 G(r)
        ↓
于是他能从"左半 = m‖0 ⊕ G(r)"里解出 m‖0 = 左半 ⊕ G(r)
        ↓
但注意：攻击者还是看不到"左半"（因为左半被 f 加密了）

嗯——单重掩码其实也没直接泄露。那为什么还要双重？

原因在"可证明安全"上：OAEP 的安全性证明依赖一个关键性质——"给定加密函数 fff 的输出，无法区分"。双重掩码（配合后面的 0k10^{k_1}0k1​ 校验）让那个归约证明能够完成。

补更实际的原因是"解密时的校验"，这个更直观：

OAEP 的解密流程（加密的逆向）：

① 用私钥解密：得到 左半 ‖ 右半

② 从右半恢复 r：  r = 右半 ⊕ H(左半)

③ 从左半恢复 m‖0^{k₁}：  m‖0^{k₁} = 左半 ⊕ G(r)

④ 检查最后 k₁ 比特是不是全 0
        ↓
    ┌───┴────┐
    ↓        ↓
   是全 0     不是全 0
    ↓        ↓
 接受，    拒绝解密
 输出 m    （判定为"非法密文/被篡改"）

第④步那个"检查全 0"就是 OAEP 的"格式校验"（对应 3.5 节 PPT 说的"规定明文消息的格式"）。

为什么这个校验有效？ 因为：

  • 合法的 OAEP 密文解密后，那 k1k_1k1​ 比特必然是全 0（这是加密时故意拼上去的）；
  • 攻击者篡改过的密文（比如 3.5 节的 c⋅xec \cdot x^ec⋅xe）解密后，那 k1k_1k1​ 比特是"乱码" —— 恰好全 0 的概率只有
2−k1=2−1282^{-k_1} = 2^{-128}2−k1​=2−128

——完全可忽略。

补所以 OAEP 用了一个非常聪明的办法：

在消息里"预留一段已知的固定值"（这里是 k1k_1k1​ 个 0），解密后检查它是否被破坏。

这就是"冗余校验（redundancy check）"——和第 6.3 节 Rabin 的"冗余问题"是同一个思路（Rabin 那里是"复制消息最后 64 比特"），也和上一册 CBC-MAC 的"长度前缀"是同类手法（在数据里嵌入可验证的结构）。

"在明文里嵌入冗余，解密后校验"是一个通用的、跨方案的防御手段，值得单独记住。

评述（PPT 第 48 页）

PPT 原文：

评述. 假设 GGG 和 HHH 都是随机函数。在实践中，GGG 和 HHH 可以使用密码 Hash 函数，例如，安全的无密钥 Hash 函数。 考虑 k0=k1=128k_0 = k_1 = 128k0​=k1​=128，则明文消息的长度为 ∣m∣=∣n−k0−k1∣=1024−256=768|m| = |n - k_0 - k_1| = 1024 - 256 = 768∣m∣=∣n−k0​−k1​∣=1024−256=768 比特，也就是说，在 RSA-OAEP 方案中有用的消息部分占 75%。

补第一段说明了 GGG 和 HHH 在实践中的实现：

理论要求 实践做法
GGG 随机函数（random oracle） 密码 Hash 函数（如 SHA-256）
HHH 随机函数 密码 Hash 函数

补"用 Hash 函数代替随机函数"是一个贯穿现代密码学的核心手法，叫**"随机预言机模型（Random Oracle Model, ROM）"**：

  • 理论上：我们只能证明"如果 GGG、HHH 是真的随机函数，则 OAEP 是安全的"（这个证明是 Bellare 和 Rogaway 在 1994 年给出的）；
  • 实践上：真随机函数不存在（它是无穷大的表格），所以用 Hash 函数代替；
  • 代价：这个替换让"可证明安全"变成了"启发式安全"——严格来说，证明只在"Hash 函数表现得像随机函数"这个假设下成立。

补注意这个思想：PPT 第 3.11 节把"Hash 函数"当零件用，而这正是第四讲（本册前半部分）讲的东西。所以第四讲和第五讲的关系是：第四讲造的零件（Hash 函数），第五讲拿来当工具（GGG、HHH）。

补第二段算了一笔"效率账"：

明文长度=k−k0−k1=1024−128−128=768 比特\text{明文长度} = k - k_0 - k_1 = 1024 - 128 - 128 = 768 \text{ 比特}明文长度=k−k0​−k1​=1024−128−128=768 比特
有用比例=7681024=75%\text{有用比例} = \frac{768}{1024} = 75\%有用比例=1024768​=75%

也就是说，OAEP 有 25% 的"填充开销"：

一个 1024 比特的 RSA 分组，OAEP 用成这样：

┌──────────────────────────────┬────────────┬────────────┐
│      明文 m（768 比特）        │ 0^{k₁}=128 │ r = 128    │
│                              │ 比特       │ 比特       │
└──────────────────────────────┴────────────┴────────────┘
└──────────────────── 总共 1024 比特 ─────────────────────┘
                     ↑
        （经过掩码和 f 之后，这个布局在密文里已经看不出来了）

补这个 75% 是"安全换效率"的典型价格。 类似的开销在不同方案里的表现：

方案 明文/分组 比例 说明
裸 RSA 100% 完全不安全
RSA-OAEP 75%（k0=k1=128k_0=k_1=128k0​=k1​=128 时） 可证明安全
PKCS#1 v1.5 ~87% 填充少，但有过 Bleichenbacher 攻击
减小 k0,k1k_0,k_1k0​,k1​ 更高 但安全性下降（k0k_0k0​ 决定"猜 rrr 的难度"，k1k_1k1​ 决定"校验强度"）

补为什么选 k0=k1=128k_0 = k_1 = 128k0​=k1​=128？ 因为它对应 128 比特的安全强度（2−1282^{-128}2−128 的猜测概率）——和当前"主流安全门槛"（128 比特）一致。这是工程上的一个"默认安全值"。

补这一节的定位，一句话总结：

RSA-OAEP 是"把裸 RSA 变成可用方案"的标准化封装。

它一次解决了前面几乎所有"使用层面"的攻击：

前面讲过的攻击 OAEP 是否防住 原因
3.3 小指数群发 ✓ rrr 让每个接收者看到"不同的实际明文"
3.3 小消息 ✓ 加掩码后"实际明文"总是接近 1024 比特
3.5 乘法特性 / 选择密文 ✓ k1k_1k1​ 个 0 的校验让"乱码密文"被拒绝
3.6 共模攻击 ✓ 同一条消息每次的"实际明文"都不同
3.10 前项搜索 ✓ 随机 rrr 让"字典"失效
3.4 小解密指数 ✗ 这是参数选择问题，OAEP 解决不了
3.7 部分密钥泄露 ✗ 同上，是密钥管理问题
3.12 定时攻击 ✗ 是"实现层"的问题，OAEP 在数学层

补这张表很重要，它说明了"OAEP 不是万能的"：

OAEP 处理的是"密文格式"层面的问题；参数选择、密钥管理、实现细节是另外三个层面，各自需要各自的措施。

密码工程的正确姿势是"分层防御"——没有哪一个方案能一次解决所有层面的问题。
