3　无密钥密码 Hash 函数：MDC

对应 PPT 第 21–43 页。这一节讲三种具体算法：MDC-2（用 DES 拼出来的）、SHA-1、MD5。前一种是"基于分组密码"的路子，后两种是"定制的"路子。

PPT 第 21 页给了"基于分组密码"这条路的动机，原文如下：

在分组密码基础上建立 Hash 函数的主要动机是：如果系统已经拥有了非常有效的分组密码，那么以分组密码作为实现 Hash 函数的主要部件，将既可以提供 Hash 函数的功能，又能使额外开销最小。

补翻译成人话：上一册你已经有了 DES、AES 这种"经过几十年检验、有硬件加速、代码成熟"的强力零件。如果你为了加 Hash 功能还要再写一套全新的算法，那就要重新做安全分析（新算法谁也不敢保证没漏洞）。于是最省事也最稳的做法是：把现成的分组密码当零件，搭出一个 Hash 函数。

这条路线上有两个代表：

算法 零件 小节
MDC-2 用 DES 当零件，搭一个无密钥 Hash 3.1
CBC-MAC 用任意分组密码 EkE_kEk​ 当零件，搭一个带密钥的 MAC 4.1

而 SHA-1、MD5 走的是另一条路：从头定制一个压缩函数，不用现成的分组密码。这条路的好处是效率更高、可以针对 Hash 的需求专门设计，代价是要自己做完整的安全分析（3.2、3.3 节）。

3.1 基于分组密码的 Hash 函数：MDC-2（PPT 第 21–24 页）

用 DES 搭 Hash 函数会遇到什么麻烦

把 DES 当零件用，第一反应是"直接拿 DES 迭代"：

Hi=E?(Mi) 或者 Hi=EHi−1(Mi)H_i = E_{?}(M_i) \text{ 或者 } H_i = E_{H_{i-1}}(M_i)Hi​=E?​(Mi​) 或者 Hi​=EHi−1​​(Mi​)

但这里马上有两个麻烦：

麻烦一：密钥长度对不上。 DES 的密钥是 64 比特（其中 56 比特有效）；而 DES 的分组也是 64 比特。所以 EHi−1(Mi)E_{H_{i-1}}(M_i)EHi−1​​(Mi​) 这种"拿链变量当密钥"的写法，要求链变量长度必须是 64 比特。这个条件还算容易满足。

麻烦二：DES 的密钥里只有 56 比特是"真密钥"。 DES 的 64 比特密钥中，每 8 比特里有 1 比特是校验位（不参与加密），所以有效密钥只有 56 比特。用 DES 的密钥表（PC-1）一过，这 8 个校验位就被丢掉了。

这就产生了一个安全漏洞：如果直接拿 64 比特链变量当 DES 密钥，那么校验位怎么变，加密结果都一样。攻击者可以随意改动这 8 个位置，Hash 值不变——这不就是一个免费送上门来的碰撞吗？（在相同的其他位下，改动校验位得到两个不同输入、同一个输出。）

MDC-2 要解决的就是这个问题。

两个函数 ggg 和 g′g'g′：把 64 比特"安全地"变成 DES 密钥（PPT 第 22 页）

PPT 原文：

假定 EKE_KEK​ 为标准 DES。对于 U=u1u2⋯u64U = u_1 u_2 \cdots u_{64}U=u1​u2​⋯u64​，定义两个函数 ggg 和 g′g'g′，将 64 比特的 UUU 映射成适合于 DES 密钥的 56 比特值如下：

g(U)=u110u4u5u6u7u9u10⋯u63,g(U) = u_1 1 0 u_4 u_5 u_6 u_7 u_9 u_{10} \cdots u_{63},g(U)=u1​10u4​u5​u6​u7​u9​u10​⋯u63​,
g′(U)=u101u4u5u6u7u9u10⋯u63。g'(U) = u_1 0 1 u_4 u_5 u_6 u_7 u_9 u_{10} \cdots u_{63}。g′(U)=u1​01u4​u5​u6​u7​u9​u10​⋯u63​。
从推荐值集合中选择两个无需保密的 64 比特常量 IVIVIV 和 IV′IV'IV′（这两个常量在 MDC 验证中也需要使用）。一组默认值为（十六进制）：IV=5252525252525252IV = \mathtt{5252525252525252}IV=5252525252525252，IV′=25252525252525IV' = \mathtt{25252525252525}IV′=25252525252525。

先看这两个公式在干什么：

输入 U:   u₁ u₂ u₃ u₄ u₅ u₆ u₇ u₈ u₉ u₁₀ ⋯⋯ u₆₃ u₆₄
                ↑↑        ↑                       ↑

g(U):     u₁  1  0  u₄ u₅ u₆ u₇  u₉ u₁₀ ⋯⋯ u₆₃
          ↑  └─┬─┘  └────┬────┘  └───────┬──────┘
       保留u₁  插入    跳过u₂u₃     跳过u₈（u₆₄也丢）
              固定值

g'(U):    u₁  0  1  u₄ u₅ u₆ u₇  u₉ u₁₀ ⋯⋯ u₆₃
                ↑↑
          只把插入的两个固定比特换成 "01"

读法：ggg 就是有选择地保留 UUU 的比特、并插入两个固定比特。

  • 保留 u1u_1u1​；
  • 插入固定比特 1 0（在 g′g'g′ 里是 0 1）；
  • 跳过 u2,u3u_2, u_3u2​,u3​，保留 u4u5u6u7u_4u_5u_6u_7u4​u5​u6​u7​；
  • 跳过 u8u_8u8​，保留 u9u10⋯u63u_9u_{10}\cdots u_{63}u9​u10​⋯u63​。

ggg 和 g′g'g′ 的唯一区别就是插入的那两个比特是 10 还是 01。这个"一个比特不同"是刻意的：它保证了两个通道的密钥不同，而且区别是最小的、可控的。

【注】原课件此处数字不自洽，不要纠结具体下标。

PPT 说 ggg 的输出是"56 比特"，但按公式逐项数一遍：111（u1u_1u1​）+2+ 2+2（插入的 10）+4+ 4+4（u4u_4u4​–u7u_7u7​）+55+ 55+55（u9u_9u9​–u63u_{63}u63​）=62= 62=62 比特，不是 56。

这说明原课件在"省略号后面省掉哪几位"这件事上没写清楚（要凑成 56，尾段应当到 u57u_{57}u57​ 附近截止，而不是 u63u_{63}u63​）。这类问题在讲"常数表"时很常见。

你要盯住的是设计意图，而不是这几个下标：ggg 的作用就是"从 64 比特链变量里剔掉那几个不适合当 DES 密钥的比特位置，再插进两个固定比特补位，得到一个 56 比特的合法 DES 密钥"。至于具体剔哪几位，不同教材的处理略有出入，但思路完全一样。

补顺带说一个"为什么不能直接拿 64 比特当密钥"的更根本理由：即使不看校验位，DES 的有效密钥空间是 2562^{56}256。如果你把 64 比特链变量原样塞给 DES，那么有 8 个比特对加密结果毫无影响——这意味着映射 Hi−1↦H_{i-1} \mapstoHi−1​↦ 加密结果 是多对一的、有 256 倍的冗余。ggg 通过"插入固定比特 + 剔掉冗余位"把这个冗余消掉，让 56 个有效比特全部由链变量决定。

两个初始值 IVIVIV 和 IV′IV'IV′

PPT 还给了两个 64 比特常量：

IV=525252525252525216,IV′=2525252525252516IV = \mathtt{5252525252525252}_{16}, \qquad IV' = \mathtt{25252525252525}_{16}IV=525252525252525216​,IV′=2525252525252516​

（勘误：PPT 上 IV′IV'IV′ 印的是 25252 52525252525，按 16 位十六进制数的规范写法应为 2525252525252525。这是原 PPT 换行造成的印刷瑕疵。）

补为什么 IVIVIV 和 IV′IV'IV′ 要这么选？ 看这两个数的模式：

IV  = 0101 0010 0101 0010 ...   (字节 0x52 重复 8 次)
      └─┬─┘
     0x52 = 0101 0010

IV' = 0010 0101 0010 0101 ...   (字节 0x25 重复 8 次)
      └─┬─┘
     0x25 = 0010 0101

注意 0x52 和 0x25 是"半字节交换"（也就是循环移位 4 位）：

0x52 = 0101 0010      0x25 = 0010 0101
       └──┬──┘             └──┬──┘
       高半字节             高半字节
       
把 0x52 的两个半字节对调（0101 0010 → 0010 0101）就得到 0x25

这样的取值有两个实际考虑：

  1. "01 01 …"的交替模式让每一位都尽量多地出现两种取值，避免某些比特位置永远固定；
  2. IVIVIV 和 IV′IV'IV′ 结构对称但不相同，保证两个通道的起点有区别，不会一开始就撞在一起。

PPT 特意强调"这两个常量在 MDC 验证中也需要使用"——意思是在做完整性验证时，接收方必须知道同样的 IVIVIV 和 IV′IV'IV′ 才能重算出同样的 Hash 值。所以它们"无需保密"但必须"约定一致"，这正好对应 PPT 原文那句"无需保密的 64 比特常量"。

补这里藏着一个重要的概念区分：IVIVIV 不需要保密，但 IVIVIV 不能随便改。 IVIVIV 的保密性无关紧要（它只是一个起点），但一致性至关重要（双方起点不同，算出的 Hash 值必然不同）。这个性质在 Hash 函数里很常见——Hash 函数的安全性完全不依赖 IVIVIV 的保密性，因为整个算法本来就是公开的、不带密钥的。

MDC-2 算法（PPT 第 23 页）

PPT 原文：

将消息 MMM 按 64 比特分组 M=[M1,M2,⋯ ,Mt]M = [M_1, M_2, \cdots, M_t]M=[M1​,M2​,⋯,Mt​]。 使用 DES 的 MDC-2 按如下步骤进行： （1）令 H0=IV,H0′=IV′H_0 = IV, H'_0 = IV'H0​=IV,H0′​=IV′。 （2）∥\|∥ 表示连接操作，CLiCL_iCLi​ 和 CRiCR_iCRi​ 表示 CiC_iCi​ 的左和右 32 比特位。输出 Hash 值是 h(M)=Ht∥Ht′h(M) = H_t \| H'_th(M)=Ht​∥Ht′​，按如下公式计算（1≤i≤t1 \le i \le t1≤i≤t）：

ki=g(Hi−1),Ci=Eki(Mi)⊕Mi;k_i = g(H_{i-1}), \qquad C_i = E_{k_i}(M_i) \oplus M_i;ki​=g(Hi−1​),Ci​=Eki​​(Mi​)⊕Mi​;
ki′=g′(Hi−1′),Ci′=Eki′(Mi)⊕Mi;k'_i = g'(H'_{i-1}), \qquad C'_i = E_{k'_i}(M_i) \oplus M_i;ki′​=g′(Hi−1′​),Ci′​=Eki′​​(Mi​)⊕Mi​;
Hi=CLi∥CRi′;Hi′=CLi′∥CRi。H_i = CL_i \| CR'_i; \qquad H'_i = CL'_i \| CR_i。Hi​=CLi​∥CRi′​;Hi′​=CLi′​∥CRi​。

这一页信息量很大，拆成四步看：

第 0 步：把消息切块

M=[M1,M2,⋯ ,Mt]M = [M_1, M_2, \cdots, M_t]M=[M1​,M2​,⋯,Mt​]

每块 64 比特（因为 DES 的分组是 64 比特）。注意这里没有提到预处理的填充和长度附加，因为这是 PPT 给的原型描述，实际实现必须补上（否则长度不匹配的输入会有歧义）。

第 1 步：初始化两条链

H0=IV,H0′=IV′H_0 = IV, \qquad H'_0 = IV'H0​=IV,H0′​=IV′

记住：MDC-2 有两条并行的链，这是它名字里"2"的由来。

第 2 步：从链变量算出两个 DES 密钥

ki=g(Hi−1),ki′=g′(Hi−1′)k_i = g(H_{i-1}), \qquad k'_i = g'(H'_{i-1})ki​=g(Hi−1​),ki′​=g′(Hi−1′​)

链条 HHH 用 ggg 导出密钥 kik_iki​，链条 H′H'H′ 用 g′g'g′ 导出密钥 ki′k'_iki′​。

第 3 步：两条链各自做一次加密，然后异或回消息

Ci=Eki(Mi)⊕Mi,Ci′=Eki′(Mi)⊕MiC_i = E_{k_i}(M_i) \oplus M_i, \qquad C'_i = E_{k'_i}(M_i) \oplus M_iCi​=Eki​​(Mi​)⊕Mi​,Ci′​=Eki′​​(Mi​)⊕Mi​

补这个 "Ek(M)⊕ME_k(M) \oplus MEk​(M)⊕M" 的写法是一整类构造的招牌，叫做 Davies–Meyer 型（或者更宽泛地说，是"把加密结果异或回输入"的写法）。它出现在几乎所有"用分组密码搭 Hash"的方案里，理由有三条：

  1. 它保证了不可逆：给定 CiC_iCi​，你想反推 MiM_iMi​，可是 MiM_iMi​ 既在 EEE 的输入里、又在异或的另一头，你自己也不知道该解哪一步。
  2. 它利用了分组密码的"混合"性质：DES 的输出看起来是均匀随机的（第 4.1 节的"评论"会说："将 MAC 分布到 MAC 空间与分组密码加密算法将密文分布到密文空间同样均匀"），所以 CiC_iCi​ 也是均匀随机的。
  3. 它比"直接用 Ek(M)E_k(M)Ek​(M)"更安全：如果只写 Ci=Eki(Mi)C_i = E_{k_i}(M_i)Ci​=Eki​​(Mi​)，那么当攻击者知道 CiC_iCi​ 和 MiM_iMi​ 时，他可以反推 Eki(Mi)E_{k_i}(M_i)Eki​​(Mi​) 从而对 kik_iki​ 做攻击。加上异或之后，等式变成 Ci⊕Mi=Eki(Mi)C_i \oplus M_i = E_{k_i}(M_i)Ci​⊕Mi​=Eki​​(Mi​)——这一条是可以的，所以安全性的关键不在"能不能反推"，而在"kik_iki​ 是由链变量 Hi−1H_{i-1}Hi−1​ 决定的、链变量又依赖于整条消息"。这也是为什么 4.2 节会说"由 MDC 构造 MAC 必须细致分析"——同样的写法，放在"消息在密钥之前"还是"密钥在消息之前"，安全性差别很大。

第 4 步：两个半块交叉交换，生成新的链变量

这是 MDC-2 最巧妙的一步：

Hi=CLi∥CRi′;Hi′=CLi′∥CRiH_i = CL_i \| CR'_i; \qquad H'_i = CL'_i \| CR_iHi​=CLi​∥CRi′​;Hi′​=CLi′​∥CRi​

     │  ↙      ↘  │
┌──────────────┬──────────────┐
│ H_i = CL_i  CR'_i            │  ← 取左链的"左半" + 右链的"右半"
└──────────────┴──────────────┘
┌──────────────┬──────────────┐
│ H'_i = CL'_i CR_i            │  ← 取右链的"左半" + 左链的"右半"
└──────────────┴──────────────┘

大白话：两条链各自算出一个 64 比特结果 CiC_iCi​ 和 Ci′C'_iCi′​，然后把它们的左右两半交叉拼起来——HiH_iHi​ 拿走 CiC_iCi​ 的左半和 Ci′C'_iCi′​ 的右半，Hi′H'_iHi′​ 拿走 Ci′C'_iCi′​ 的左半和 CiC_iCi​ 的右半。

补为什么非要"交叉交换"？这一步是 MDC-2 抗碰撞的关键。 如果没有这一步，两条链就是完全独立的——各自跑各自的 DES，互不相干。那么攻击者只要攻破其中一条就够了（比如专门制造 HtH_tHt​ 的碰撞），另一条链根本不起作用，2642^{64}264 的强度只剩下 64 比特，而输出是 128 比特——白白浪费了一半的输出长度。

有了交叉交换之后，两条链被绑在一起了：HiH_iHi​ 里含有上游右链的比特，Hi′H'_iHi′​ 里含有上游左链的比特。要制造最终输出的碰撞（Ht∥Ht′H_t \| H'_tHt​∥Ht′​ 撞上），就必须让两条链同时回到相同的状态。这个"同时"就是难度所在——把两条链的碰撞概率相乘，从而把强度从 2642^{64}264 抬到 21282^{128}2128 量级。

补输出的拼法：PPT 说"输出 Hash 值是 h(M)=Ht∥Ht′h(M) = H_t \| H'_th(M)=Ht​∥Ht′​"，也就是把最后两条链的结果首尾相接：

h(M) = H_t ‖ H'_t
       └64比特┘└64比特┘
       └─── 128 比特 ───┘

输出 128 比特。按 2.2 节事实 6，抗碰撞强度大约是 2128/2=2642^{128/2} = 2^{64}2128/2=264——这就是 MDC-2 的安全强度，也是它只适合当"过渡方案"的原因。它真正的价值在于：用现成的 DES 就能得到一个 128 比特的 Hash 函数，而且抗碰撞强度正好等于 DES 本身的密钥强度（256≈2642^{56} \approx 2^{64}256≈264 量级），没有短板。

补MDC-2 这个名字里的"2"还有一层含义：它是 MDC-2，也就是"第 2 代 MDC"。更早的 MDC-1 因为没有做交叉交换，安全性不足（上面说的那条理由），所以实际使用的是 MDC-2。这个"1 → 2"的改进过程本身很值得记：同一套零件，加一步交叉交换，强度提升一个量级。

补MDC-2 的"两个密码调用"是它的成本来源：每处理 64 比特消息要跑两次 DES。相比后面 SHA-1/MD5 这类定制算法，MDC-2 明显更慢。所以它主要出现在"已经有 DES 硬件、不想再引入新算法"的场景里，属于工程折中方案。
